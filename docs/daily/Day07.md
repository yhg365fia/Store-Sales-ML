### 날짜 피처와 과거 판매량 피처의 차이

- 날짜 피처는 요일·월·주말 여부처럼 반복되는 시간 조건을 알려준다.
- Lag는 **해당 매장·상품군이 실제로 과거에 얼마나 팔렸는지**를 직접 알려준다.
- 기존에는 판매량을 학습 정답으로만 사용했지만, Lag를 추가하면서 과거 판매량을 입력 정보로도 활용하게 됐다.
- 54개 매장 × 33개 상품군으로 총 1,782개 시계열이 존재하며, 각 시계열 안에서 과거 값을 가져온다.
- Lag를 추가한다고 매장·상품군 조합이나 행 수가 늘어나는 것은 아니다. **기존 각 행에 과거 판매량 컬럼이 추가되는 것**이다.
- 이번에는 세 개의 Lag를 추가해 모델 입력이 23개에서 26개로 늘었다. `family`는 개별 상품이 아니라 상품군이라는 점도 구분했다.

### 16일·21일·28일 Lag를 선택한 이유

- 16일은 현재처럼 **16일 전체를 한 번에 예측하고 중간에 실제 판매량을 받지 않는 방식에서 사용할 수 있는 최소 고정 Lag**다.
- 21일과 28일은 각각 3주 전과 4주 전으로, 예측일과 같은 요일의 판매량을 제공한다.
- EDA에서 요일별 판매량 차이를 확인했으므로 같은 요일의 과거 값을 피처 후보로 잡았다.
- 예를 들어 8월 31일을 예측할 때 `lag_16`은 이미 알고 있는 8월 15일 판매량을 가져온다.
- 반면 `lag_7`은 아직 알 수 없는 8월 24일 실제 판매량이 필요하므로 현재 방식에 그대로 사용할 수 없다.
- **이번 Lag 값은 예측 기간과 주간 패턴을 근거로 선택한 초기 후보이며, 최적 조합이라고 확인한 것은 아니다.**

### groupby와 shift로 과거 판매량 연결하기

```python
grouped_sales = df.groupby(
    ["store_nbr", "family"],
    observed=True,
)["sales"]

for lag in lags:
    df[f"sales_lag_{lag}"] = grouped_sales.shift(lag)
```

- `groupby()`는 같은 매장과 상품군의 행끼리 묶고, `["sales"]`는 그 그룹에서 판매량을 선택한다. 이 단계에서 평균이나 합계를 계산하는 것은 아니다.
- `observed=True`는 범주형 조합 중 실제 데이터에 존재하는 조합을 대상으로 한다.
- `shift(lag)`는 각 그룹 안에서 판매량을 lag행만큼 이동시킨다. 따라서 다른 매장이나 상품군의 판매량이 넘어오지 않는다.
- **`shift(16)`은 16일 전이 아니라 16행 전을 가져온다.** 날짜순 정렬과 하루 한 행이라는 조건이 충족돼야 16일 전으로 해석할 수 있다.
- 그래서 `date × store_nbr × family` 키 중복을 검사하고, 그룹별 `date.diff()`가 첫 행을 제외하고 모두 1일인지 확인했다.
- `.diff()`는 현재 행과 이전 행의 차이를 계산한다. 날짜 차이가 2일이라면 중간 날짜가 빠져 있다는 의미다.

### 초기 Lag 결측치는 오류가 아니다

- 각 시계열의 처음에는 참조할 과거 기록이 없으므로 Lag 결측치가 생긴다.

| 피처 | 예상 결측치 | 실제 결측치 |
| --- | ---: | ---: |
| `sales_lag_16` | 1,782 × 16 | 28,512 |
| `sales_lag_21` | 1,782 × 21 | 37,422 |
| `sales_lag_28` | 1,782 × 28 | 49,896 |

- 실제 결측치 수가 예상과 일치했고, 코드에서는 결측치가 각 그룹의 시작 부분에만 존재하는지도 검증했다.
- 과거 기록이 없다는 것과 실제로 판매량이 0이었다는 것은 다르므로, **초기 Lag NaN을 0으로 채우지 않고 유지**했다.
- 기존 입력 피처와 Validation의 Lag에는 결측치가 없어야 한다는 검사는 유지했다.
- 결측치는 무조건 제거하는 것이 아니라 **왜 생겼으며 어떤 의미를 가지는지에 따라 처리해야 한다**는 점을 배웠다.

### Fold 분리 전에 Lag를 만들어도 되는 조건

- 전체 Train에 먼저 Lag를 적용한 뒤 Fold를 나누면 누수가 생기지 않는지 확인했다.
- 핵심은 계산 순서 자체보다 **검증 행의 피처가 어느 날짜의 판매량을 참조하는지**다.
- Fold 3의 검증 마지막 날인 8월 15일도 `lag_16`은 학습 마지막 날인 7월 30일의 판매량을 가져온다.
- 따라서 검증 구간이 16일이고 최소 Lag가 16일이면, 모든 Validation 행이 해당 Fold의 학습 기간 판매량만 참조한다.
- 이 조건에서 전체 기간에 Lag를 먼저 생성해도 안전하다. 검증 기간을 늘리거나 Lag를 줄이면 다시 확인해야 한다.
- 반대로 Validation만 잘라서 `shift()`하면 Train의 과거 기록을 가져오지 못한다.
- **시간순으로 나누는 것뿐 아니라, 피처 생성 과정에서도 예측 시점에 알 수 있는 정보만 사용해야 한다.**

### Lag 추가 후 결과와 비교

- 같은 3개 Fold, 모델 파라미터, Early Stopping 조건을 유지하고 Lag 세 개만 추가해 비교했다.

| 구간 | Lag 추가 전 RMSLE | Lag 추가 후 RMSLE | 상대 개선율 |
| --- | ---: | ---: | ---: |
| Fold 1 | 0.417734 | **0.396964** | 4.97% |
| Fold 2 | 0.422125 | **0.408225** | 3.29% |
| Fold 3 | 0.412261 | **0.406133** | 1.49% |
| 평균 | 0.417374 | **0.403774** | **3.26%** |

- 세 Fold 모두 개선돼 이번 검증에서는 과거 판매량을 입력으로 제공한 효과가 일관되게 나타났다.
- 직전 최고와 같은 검증 기간인 Fold 3은 0.006128 감소했다.
- 다만 표준편차는 0.004942에서 0.005990으로 증가했다. **평균 오차가 줄었다고 구간별 점수 차이까지 줄어든 것은 아니다.**
- Best Iteration은 Fold별로 949 / 1,768 / 2,387이었으며, 모두 Lag 추가 전보다 적었다.
- 더 적은 트리로 더 낮은 검증 오차에 도달했지만, 실행 시간을 별도로 측정하지 않았으므로 실제 시간 단축까지 확인한 것은 아니다.
- `sales_lag_16`, `sales_lag_21`, `sales_lag_28`은 평균 split 기준 각각 4위, 7위, 8위였다.
- 다만 이번에 검증한 것은 **세 Lag를 함께 추가한 효과**다. 각각의 기여도나 최적 Lag는 따로 비교해야 한다.

### Rolling과 EMA로 확장할 방향

- Rolling은 일정 기간을 묶는 방식이고, 평균을 계산하면 Rolling mean, 최솟값은 Rolling min, 표준편차는 Rolling std다.
- Rolling mean은 과거 구간의 평균 판매 수준을, Rolling std는 판매량이 얼마나 흔들렸는지를 표현한다.
- EMA는 최근 값에 더 큰 가중치를 주고 오래된 값의 가중치를 점차 줄이는 지수이동평균이다.
- 같은 기간을 동일하게 반영하는 Rolling mean과 최근 변화에 더 무게를 두는 EMA는 서로 다른 표현이다.
- 변화량은 두 과거 시점의 판매량 차이, 변화율은 이전 판매량 대비 상대적인 증감을 나타낸다. 판매량이 0이면 일반 변화율은 정의되지 않으므로 처리 방식이 필요하다.
- 현재는 **Lag만 구현·검증했고, Rolling과 EMA는 개념과 계산 방식을 이해한 단계**다.
- 다음에는 Rolling mean을 추가하고, 이후 EMA와 Rolling min / std를 하나씩 비교하기로 했다.
- 이 피처들도 현재 예측 방식에 맞춰 먼저 판매량을 충분히 이동시킨 뒤 계산해야 한다.

### Lag를 만드는 기간과 학습 기간은 다르다

- 전체 기간에 Lag를 만들면 과거 행에는 그 당시의 과거 판매량이 붙는다. 오래된 행에 현재 판매량을 넣는 것이 아니다.
- 최근 1년이나 3개월의 패턴만 학습하고 싶다면, **Lag 생성 범위보다 모델에 사용할 학습 기간을 제한하는 실험**으로 구분할 수 있다.
- Lag를 먼저 생성한 뒤 학습 기간을 잘라야, 학습 시작일 바로 앞의 과거 기록도 활용할 수 있다.
- 이번에는 학습 기간을 유지해서 Lag 효과부터 확인했다. 기간 제한은 별도 실험으로 남겼다.

### 전체 학습과 Test 예측을 위한 코드 준비

- 최종 예측에서는 Train과 Test를 연결해 Lag를 계산한 뒤, 다시 학습용 Train과 예측용 Test로 분리하도록 코드를 준비했다.
- Test의 `sales`는 알 수 없으므로 NaN으로 유지한다. 0으로 넣으면 실제 판매량처럼 취급될 수 있다.
- 현재 Lag 16·21·28일은 Test 마지막 날까지 Train의 실제 판매량만 참조하므로 Test 정답 없이 계산할 수 있다.
- Test를 버리는 것이 아니라 **학습에서는 제외하고 예측용으로 보관하는 것**이다.
- Lag 생성 중 정렬로 행 순서가 바뀌므로 원래 Test 순서를 복원하고, 최종 제출파일은 `id`로 예측값을 연결하도록 했다.
- `main()`이 전체 Train, Test, holidays를 반환하는 구조에 맞춰, 이전처럼 Validation을 별도로 다시 합치는 코드를 수정했다.
- Validation 없는 전체 학습에서는 Early Stopping을 사용할 검증 정답이 없으므로, 백테스트를 근거로 학습 횟수를 미리 정해야 한다.
- 기존 `BEST_ITERATION=4044`는 Lag 추가 전 결과이므로 최종 실행 전에 다시 결정해야 한다.
- **오늘은 제출 코드를 준비했으며, Lag 모델 전체 재학습이나 새로운 Kaggle 제출을 완료한 것은 아니다.**

### 실험 기록과 비교 기준

- 실험 번호는 실행 순서에 따라 초기 모델 01, 반복 횟수 증가 02, 매장·지역 피처 반영 및 3-Fold 백테스트 03, Lag 추가 04로 정리했다.
- 아직 실행하지 않은 Rolling / EMA는 번호 없는 예정 항목으로 남겼다.
- 기존 실험과 같은 검증 구간인지, 피처 외에 모델 설정도 바뀌었는지를 함께 기록해야 점수 차이를 해석할 수 있다.
- 로그 타깃의 RMSE와 복원 후 RMSLE는 음수 예측 보정 때문에 소폭 다를 수 있으므로 결과를 구분했다.
- Feature Importance는 사용 빈도이며, 모델의 트리 수가 달라지면 split 횟수도 달라진다. 기존 피처의 split 감소를 곧바로 기여도 감소로 해석하지 않는다.
- 다음 피처 추가 실험의 기준은 **평균 RMSLE 0.403774, Fold 3 RMSLE 0.406133**이다.

### 느낀 점

- Day06이 매장 정보의 의미와 중복 가능성을 탐색한 날이었다면, Day07은 **추가한 정보를 모델에 연결하고 여러 시점의 검증으로 가설을 확인한 날**이었다.
- Lag를 처음에는 과거 판매량 컬럼을 붙이는 작업으로 생각했지만, 예측 기간과 실제로 알 수 있는 날짜를 함께 고려해야 한다는 점을 이해했다.
- 특히 Fold 분리 전에 계산해도 되는지, Train과 Test를 왜 합치는지 질문하면서 데이터 누수를 코드 실행 순서보다 정보의 참조 시점으로 보게 됐다.
- 결측치도 무조건 없애야 할 값이 아니라, 과거 기록 부족이라는 의미가 있을 수 있음을 확인했다.
- 실제로 세 Fold 모두 개선되면서, 과거 판매량을 입력으로 제공하는 가설이 이번 실험에서는 유효하다는 근거를 얻었다.
- 한 줄 정리: **시계열 피처는 과거 값을 추가하는 것뿐 아니라, 예측 시점에 알 수 있는 정보만 연결하고 같은 조건의 백테스트로 효과를 확인하는 과정이다.**
