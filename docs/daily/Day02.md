## 판단 / 배운 점

### 데이터 이해
- Store Sales의 `test`는 학습 데이터 바로 다음 기간을 예측하는 구조이므로 **train-test 날짜 경계를 정확히 확인하는 것이 중요하다.**
- 날짜는 단순 ID가 아니라 요일, 공휴일, 계절성과 같은 여러 패턴을 담을 수 있는 핵심 변수다.
- 요일별 평균 판매량을 비교했을 때 **목요일이 가장 낮고 주말인 토·일요일에 크게 증가하며 일요일이 가장 높게 나타났다.**
- 따라서 `dayofweek`는 이후 모델링에서 활용할 가치가 있는 기본적인 시간 feature라고 판단했다.
- 공휴일 데이터는 같은 의미의 이벤트라도 `Navidad-4`, `Navidad-3`, `Navidad-2`, `Navidad-1`, `Navidad`, `Navidad+1`처럼 여러 날짜로 나뉘어 기록되어 있었다.
- 단순히 `description` 하나하나를 별개 범주로 보는 것보다 **비슷한 이벤트를 의미 단위로 묶는 것이 데이터 구조를 이해하기 더 쉬웠다.**

### 공휴일 / 이벤트
- `locale`은 이벤트가 적용되는 범위를 나타낸다.
  - `National`: 전국
  - `Regional`: 특정 지역
  - `Local`: 특정 도시
- 따라서 공휴일이라고 해서 모든 매장에 동일하게 적용하면 안 된다.
- 특히 Local 이벤트는 `stores.csv`의 도시 정보와 연결해야 실제 영향을 받는 매장만 구분할 수 있다.
- `event_group`으로 묶어 보니 지역 창립기념일, 지역 기념일, 독립기념일, 크리스마스 등의 구조가 훨씬 명확하게 보였다.
- 이벤트 등장 횟수가 많다고 반드시 판매량 영향이 큰 것은 아니다.
  - 예를 들어 `Black Friday`, `Cyber Monday`는 등장 횟수는 적지만 판매량에 미치는 영향은 클 수도 있다.
- 실제 예측 기간의 공휴일을 확인했을 때 `2017-08-24`의 `Fundacion de Ambato`가 포함되어 있었다.
  - `Local`
  - `Ambato`
  - `City Foundation`
  - `transferred = False`
- 따라서 이 이벤트는 전체 매장이 아니라 **Ambato에 있는 매장에만 적용되는 이벤트**로 보는 것이 맞다.

### EDA 방법
- 시계열에서는 전체 데이터 분포만 보는 것뿐 아니라 **실제로 예측할 미래 구간에 어떤 조건이 존재하는지 확인하는 것도 중요하다.**
- 범주가 너무 세분화되어 있으면 원본 값을 그대로 모두 분석하기보다 의미가 비슷한 항목을 상위 그룹으로 묶어 구조를 먼저 이해할 수 있다.
- 하지만 원본 정보를 완전히 버리는 것은 아니고 필요하면 `description`으로 다시 돌아갈 수 있도록 유지하는 것이 좋다.
- 공휴일 데이터처럼 한 날짜에 여러 행이 존재하는 경우에는 `date` 기준 aggregation을 통해 한 날짜에 어떤 이벤트들이 겹치는지 확인할 수 있다.
- EDA에서 모든 정보를 끝까지 파고들 필요는 없다. **모델링에 필요한 가설을 만들 정도로 구조를 이해했다면 일단 넘어가고, 필요할 때 다시 돌아오는 것이 효율적이다.**

### 모델링 아이디어
- 날짜에서 다음과 같은 기본 feature를 만들 수 있다.
  - `year`
  - `month`
  - `day`
  - `dayofweek`
  - 주말 여부
- 공휴일은 단순 `is_holiday` 하나보다 필요하면 다음 정보를 함께 활용할 수 있다.
  - 이벤트 종류
  - `event_group`
  - National / Regional / Local 범위
  - 공휴일 이동 여부
- Local / Regional 이벤트는 `stores.csv`의 도시·지역 정보와 연결해야 한다.
- 크리스마스처럼 하루가 아니라 전후 여러 날에 영향을 줄 가능성이 있는 이벤트는 이후 필요하면 **이벤트 전후 거리** 형태의 feature도 생각해볼 수 있다.
- 다만 처음부터 복잡하게 만들기보다 baseline 모델에서는 기본적인 날짜 feature와 공휴일 정보부터 시작하고 성능을 보면서 확장하는 것이 좋다고 판단했다.

### 느낀 점
- Day01에는 전체 데이터를 넓게 보면서 판매량 분포, 매장, 상품군, 프로모션 등의 큰 구조를 이해했다면, Day02에는 **빠진 부분을 확인하고 EDA를 실제 모델링 단계로 연결하는 작업**을 했다.
- 특히 단순히 공휴일 파일을 보는 데서 끝나는 것이 아니라, `description`이 너무 세분화되어 있다는 문제를 보고 직접 `event_group`으로 묶어 보는 방향을 생각했다.
- 또한 전체 공휴일을 전부 분석하는 것보다 **내가 실제로 예측해야 하는 test 기간에 어떤 이벤트가 있는지를 확인하는 것이 더 중요하다**고 판단했다.
- 어제보다 데이터를 무작정 많이 보는 것보다 어떤 분석이 실제 예측에 필요한지를 기준으로 EDA 범위를 끊는 감각이 조금 생긴 것 같다.
- 한 줄 정리: **EDA는 모든 것을 분석하는 작업이 아니라, 모델링에 필요한 만큼 데이터를 이해하고 필요한 가설을 남기는 작업이다.**
