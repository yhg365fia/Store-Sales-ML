- 수동 파라미터 비교에서는 Baseline을 포함한 **6개 구성**을 비교했다. 정규화를 강화하거나 트리 복잡도를 낮춘 5개 변경안 모두 3-Fold 평균 RMSLE가 악화됐다.

- 반면 `base23_payday_lag364_fixed`라는 이름의 제출에서 **Public 0.43626**을 확인했다. 이번에 확인한 제출 중 가장 낮은 점수다. 다만 파일명만으로 정확한 피처 목록이나 Lag 364의 단독 기여를 확정하지 않았다.
- 새로운 실험·제출 결과를 기존 `experiment.md`에 **Exp 31~34**로 추가하고, 검증 결과와 해석을 구분해 정리했다.

### 1. Oil Raw 수동 하이퍼파라미터 비교 — 규제를 강화해도 평균 성능은 개선되지 않음

Day13의 외부 피처 5종 실험과 구분되는 **이후의 Oil Raw 30개 파라미터 비교 결과**를 확인했다. 원본 `score_summary.csv`에는 Baseline과 단독 변경 4종, 조합 변경 1종이 정리되어 있다.

| 구성 | 평균 Valid RMSLE | Baseline 대비 Δ | 개선 Fold | Train sample과의 평균 Gap |
|---|---:|---:|---:|---:|
| **Baseline** | **0.393282** | — | — | 0.033561 |
| `B_min_child_150` | 0.394260 | +0.000978 | 1/3 | 0.030855 |
| `D_reg_lambda_5` | 0.394896 | +0.001614 | 1/3 | 0.026772 |
| `E_A_B_D` | 0.396162 | +0.002880 | 0/3 | 0.015779 |
| `C_max_depth_6` | 0.396632 | +0.003350 | 1/3 | −0.004128 |
| `A_num_leaves_15` | 0.397644 | +0.004362 | 0/3 | 0.017818 |

- **5개 변경안 모두** Baseline 평균 0.393282보다 높았다. 가장 나은 변경안인 `min_child_samples=150`도 +0.000978 악화됐다.
- `max_depth=6`은 Train sample RMSLE가 Validation RMSLE보다 높아 Gap이 음수였지만, 정작 Validation 성능은 Baseline보다 +0.003350 나빴다.
- **일반화 갭이 작아지는 것과 Validation 성능이 개선되는 것은 같은 일이 아니다.** 특히 여기서 Train 점수는 전체 Train이 아닌 in-sample Train sample 기준이다.
- 이 비교의 Baseline **0.393282**는 Day13에서 사용했던 **Payday 29개 Baseline 0.394011**과 다르다. 피처 구성·실행 단계가 달라 두 값을 같은 Baseline으로 혼동하지 않았다.
- 원본 요약에는 각 구성의 Fold별 점수와 전체 하이퍼파라미터 목록이 없어, 변경 이름에 없는 상세 설정을 추측하지 않았다.

### 2. Oil Raw 30개 Optuna 실험 — Local CV 개선과 Public 악화

**실험 구성:** 기존 Payday 29개 피처에 `dcoilwtico`를 추가한 30개 피처, LightGBM, Early Stopping 150, 16일씩 3-Fold 시계열 검증.

| Fold | Validation 기간 | Best Trial 8 RMSLE | Best Iteration | Train sample RMSLE | Gap |
|---|---|---:|---:|---:|---:|
| Fold 1 | 2017-06-29 ~ 07-14 | **0.378120** | 2,721 | 0.342491 | 0.035629 |
| Fold 2 | 2017-07-15 ~ 07-30 | 0.396141 | 2,149 | 0.349238 | 0.046903 |
| Fold 3 | 2017-07-31 ~ 08-15 | 0.400034 | 2,417 | 0.348697 | 0.051337 |
| **평균** | | **0.391431** | | | |

- 첨부 Fold CSV에는 **12개 Trial의 36개 Fold 결과**가 기록되어 있었다. 그중 평균 RMSLE 최저는 **Trial 8**, 표본 표준편차는 **0.011692**였다.
- Best Trial의 주요 파라미터는 `num_leaves=68`, `min_child_samples=70`, `max_depth=-1`, `learning_rate=0.075477`, `reg_alpha=3.308396`, `reg_lambda=0.946449`, `colsample_bytree=0.954769`였다.
- JSON의 최종 전체 학습 반복 횟수는 **2,417회**로 기록됐다. 이는 Fold별 Best Iteration 2,721·2,149·2,417의 중앙값과 일치한다.
- 이전 수동 비교 Baseline과 비교하면 Local 평균 RMSLE가 **0.393282 → 0.391431(−0.001851)**로 낮아졌다. 다만 두 실행의 전체 파이프라인 일치 여부는 추가 로그가 필요하다.
- 그러나 `submission_optuna_oil_raw_trial8_20261026_162718_706124.csv`의 Kaggle Public은 **0.54512**였다. 기존 `submission_oil_raw.csv`의 **0.50336**보다 **+0.04176 악화**됐다.

**해석:** Optuna가 선택에 사용한 3-Fold에서는 성능이 좋아졌지만, 실제 Kaggle 공개 평가 구간으로 이어지지 않았다. 반복 탐색에 따른 CV 선택 편향, 마지막 Test 구간의 분포 차이, Oil 병합·보간이나 최종 제출 코드의 불일치 등이 가능한 설명이지만, **어느 것이 실제 원인인지는 확인되지 않았다.**

### 3. Lag-only 26개 Optuna 실험 — Oil을 제외해도 Public 악화

Oil의 입력 가용성 문제를 분리해 생각하기 위해, **기본 23개 피처 + Sales Lag 16·21·28 = 26개**인 Lag-only 구성의 튜닝 결과도 확인했다. `dayofyear`, Payday, Oil은 이 모델에 포함되지 않는다.

| Fold | Validation 기간 | Best Trial 12 RMSLE | Best Iteration | Train sample RMSLE | Gap |
|---|---|---:|---:|---:|---:|
| Fold 1 | 2017-06-29 ~ 07-14 | **0.379546** | 3,592 | 0.350208 | 0.029338 |
| Fold 2 | 2017-07-15 ~ 07-30 | 0.398271 | 2,714 | 0.357842 | 0.040429 |
| Fold 3 | 2017-07-31 ~ 08-15 | 0.401725 | 4,138 | 0.349808 | 0.051917 |
| **평균** | | **0.393181** | | | |

- 첨부 Fold CSV의 **11개 Trial, 33개 Fold 결과**에서 **Trial 12**가 평균 RMSLE 최저였다. 표본 표준편차는 **0.011934**였다.
- 주요 파라미터는 `num_leaves=68`, `min_child_samples=130`, `max_depth=12`, `learning_rate=0.065027`, `reg_alpha=1.313450`, `reg_lambda=1.899669`, `colsample_bytree=0.978959`였다.
- JSON에 적힌 최종 학습 횟수 **3,592회**는 Best Iteration 3,592·2,714·4,138의 중앙값과 일치한다.
- 같은 날짜 Fold를 사용한 Oil Raw Trial 8의 0.391431보다 평균이 **0.001749 높았다.** 다만 최적화된 파라미터와 전체 피처 구성이 모두 다르므로, 이것을 **Oil 피처 하나의 순수한 효과**로 해석할 수 없다.
- `submission_optuna_lag_only_trial12_20261026_162718_706124.csv`의 Public은 **0.49487**이었다. 기존 Lag-only 제출의 **0.46161**보다 **+0.03326 악화**됐다.

**해석:** Oil을 제외한 Lag-only에서도 Optuna Best Trial이 이전 제출보다 좋은 Public 점수를 얻지 못했다. 그러므로 **Oil 피처가 Public 악화의 유일한 원인이라고 단정할 수 없다.** 원래 Lag-only 제출과 튜닝 제출은 학습률·규제·최종 반복 횟수가 달라, 동일한 예측 코드로 재현하면서 비교할 필요가 있다.

### 4. Kaggle Public 제출 결과 비교 — Lag 364 관련 모델 0.43626

2026년 10월 26일에 제공된 Kaggle 제출 화면에서 다음 5개 제출의 완료 상태와 Public Score를 확인했다.

| 제출 모델/파일 | Public RMSLE | 비고 |
|---|---:|---|
| **`submission_base23_payday_lag364_fixed_20261026_192315.csv`** | **0.43626** | 이번에 확인한 제출 중 최저 |
| `submission_ts_best_iter5000.csv` | 0.48431 | 과거 Rolling 기반 제출과 점수 일치 |
| `submission_optuna_lag_only_trial12_20261026_162718_706124.csv` | 0.49487 | Lag-only Optuna |
| `submission_oil_raw.csv` | 0.50336 | 기존 Oil Raw 제출 |
| `submission_optuna_oil_raw_trial8_20261026_162718_706124.csv` | 0.54512 | Oil Raw Optuna |

- 별도로 기존 Exp 18에서 확인한 **Lag-only Public 0.46161**과 비교하면, 이번 0.43626은 **0.02535(약 5.49%) 낮다.**
- `base23_payday_lag364_fixed`라는 파일명으로 **Base23·Payday·Lag 364 관련 구성을 사용했을 가능성**을 알 수 있지만, 정확한 피처 목록·개수·최종 반복 횟수·실제 수정 내용을 확인한 것은 아니다.
- 과거 **Exp 16**에서는 Rolling mean을 포함한 Exp 13에 Lag 364를 추가하자 Local CV가 0.391424 → 0.392009로 악화됐다. 이번 제출과는 **Baseline 자체가 다르므로** 결과가 모순이라고 보지 않았다.
- 지금 확인한 0.43626은 **Public Score**이지 Private Score가 아니다. 해당 모델의 별도 3-Fold 결과도 아직 확보하지 못했다.

**해석:** 현재 제출 화면에서 가장 유망한 것은 Lag 364 관련 모델이다. 그러나 **Lag 364를 넣었기 때문에 0.43626이 나왔다**는 인과 결론은 아직 불가능하다. 실제 개선 요인을 파악하려면 같은 Base23 + Payday 구성에서 Lag 364만 추가·제거하는 독립 실험이 필요하다.

### 5. Local CV와 Kaggle Public의 순위가 달라진 문제

| 모델 | Local 3-Fold 평균 | Kaggle Public | 현재 판단 |
|---|---:|---:|---|
| Payday 29개 과거 Baseline | 0.394011 | 동일 구성 점수 미확인 | 과거 피처 실험 비교 기준 |
| Oil Raw 수동 비교 Baseline | 0.393282 | 0.50336 참조* | 실행 설정 동일성 추가 확인 |
| Oil Raw Optuna Trial 8 | **0.391431** | **0.54512** | Local 개선, Public 악화 |
| Lag-only Optuna Trial 12 | 0.393181 | 0.49487 | 기존 Lag-only Public보다 악화 |
| Lag 364 관련 제출 | 미확인 | **0.43626** | Public 최저, CV 재현 필요 |

\* 0.50336은 Oil Raw 이전 제출 참조 점수다. 수동 비교 Baseline과 제출 모델의 전체 설정 동일성은 확인되지 않았다.

- **CV 성능이 가장 낮은 모델이 Public에서도 가장 낮은 모델은 아니었다.** 특히 Oil Raw Optuna는 Fold 평균을 개선했지만 Public에서는 크게 악화됐다.
- 이 결과만으로 과적합, 시간 누수, 데이터 드리프트, 코드 오류 중 무엇이 원인인지 확정할 수 없다.
- 16일 일괄 예측에서는 Fold Validation을 만들 때와 최종 Test 피처를 만들 때 **동일한 시점의 이용 가능 정보만 사용했는지** 중요하다.
- 탐색에 사용한 3-Fold에서 Best Trial을 반복적으로 선택하면 해당 Fold에 맞춰질 수 있으므로, 가능하면 **탐색에 사용하지 않은 시간 홀드아웃**에서도 비교해야 한다.
- Public 점수를 반복 확인하며 모델을 고르는 것도 공개 평가 구간에 맞추는 행동이 될 수 있다. Public 최저를 곧바로 최종 Private 성능이 가장 좋은 모델로 간주하지 않는다.

### 6. 피처·전처리·누수 점검 사항 다시 정리

| 점검 항목 | 이번에 정리한 내용 |
|---|---|
| Sales Lag 16·21·28 | 16일 예측 시작 시점에 이미 관측한 값으로 생성해야 함 |
| Sales Lag 364 | 52주 전 값으로 요일 정렬 가능. 최초 학습 구간 결측과 실제 조인 시점 QC 필요 |
| Oil Raw | Day13에서 확인한 날짜별 Test Oil 병합 방식과 CV 처리 방식의 일치 여부 재검증 |
| Oil 보간 | Fold 경계를 넘는 사후 관측값을 사용했는지 확인. 아직 누수 발생 여부는 미확인 |
| Train sample Gap | 과적합을 판단하는 보조 지표이며, Gap이 작다고 Valid가 좋은 것은 아님 |
| Best Iteration | Fold별 최적 횟수와 전체 Train 최종 반복 횟수를 분리해 기록 |
| 범주형·피처 순서 | Train/Validation/Test의 범주 기준과 열 순서, 결측/무한대 처리 일치 확인 필요 |
| 제출 CSV | 28,512행, `id` 순서·중복, NaN/음수/무한대 예측과 역변환 검사 필요 |

- Lag 364는 16일보다 충분히 이전의 Sales를 참조하므로 **올바르게 구현하면** 직접적인 미래 타깃 사용 없이 생성할 수 있다. 하지만 최신 제출 코드의 실제 구현은 확보되지 않았다.
- 54개 매장 × 33개 상품군의 완전한 일별 패널이라면 Lag 364 초기 결측은 **1,782 × 364 = 648,648개가 예상**된다. 이는 계산상 기대값이지 최신 모델의 실측 QC 값이 아니다.
- Day13에서 강조했던 것처럼 **오류를 없애는 것과 올바른 데이터를 입력하는 것은 다른 일**이다. 이번에는 한 단계 더 나아가, **좋은 Local 점수를 얻는 것과 실제 예측 구간에서 잘 작동하는 것도 다른 문제**임을 확인했다.

### 7. 실험 결과 문서 업데이트

- 기존 실험 기록의 **가설 → 변경 사항 → 결과 → 해석 → 다음 실험** 형식을 유지하며 신규 결과를 추가했다.
- Exp 31에는 Oil Raw 수동 파라미터 비교, Exp 32에는 Oil Raw Optuna, Exp 33에는 Lag-only Optuna, Exp 34에는 최신 Kaggle Public 및 Lag 364 관련 제출 결과를 기록했다.
- Optuna 두 실험은 **Best Trial만이 아니라 첨부 CSV에 있는 모든 Trial의 Fold별 RMSLE**를 정리했다. 하지만 전체 Trial의 개별 파라미터는 없으므로 재현 가능 항목과 추가 확보할 항목을 나눴다.
- Day13의 외부 피처 5종은 여전히 **당시 실행의 Fold별 원본 점수가 확인되지 않았다.** 이후 Oil Raw 튜닝 결과를 Day13의 최초 실험 결과로 소급 대입하지 않았다.
- 확인되지 않은 학습 코드 변경, 누수 원인, Public 개선 원인은 완료된 실험처럼 기록하지 않았다.

## 판단 / 배운 점

### 1. Local CV가 좋아져도 실제 Kaggle 점수가 좋아지는 것은 아니다

- Oil Raw Optuna는 3-Fold 평균을 0.001851 개선했지만 Public은 0.04176 악화됐다.
- Lag-only Optuna도 내부 Best Trial을 선택했지만 기존 Lag-only Public에 미치지 못했다.
- **CV 개선을 모델 채택의 유일한 기준으로 사용하지 않고, 검증 구간과 제출 파이프라인의 차이를 확인해야 한다.**

### 2. 하이퍼파라미터 튜닝과 피처 추가의 효과는 구분해야 한다

- Optuna Oil Raw와 Lag-only는 피처뿐 아니라 학습률·정규화·트리 복잡도·최종 반복 횟수가 다르다.
- 수동 비교에서는 규제를 강화해 Train/Valid Gap을 줄여도 Validation 점수가 개선되지 않았다.
- **하나의 변경이 실제로 어떤 영향을 주었는지는 다른 조건을 고정한 비교 실험에서만 판단할 수 있다.**

### 3. Public 최저 모델도 원인 분석과 재현이 필요하다

- Lag 364 관련 제출의 **0.43626**은 지금까지 확인한 중요한 성과다.
- 그러나 파일명과 점수만으로 어떤 피처가 얼마나 기여했는지, CV에서도 안정적인지 알 수 없다.
- **좋은 점수를 낸 코드를 다시 실행해 같은 결과를 만들 수 있는지**가 다음 단계의 핵심이다.

### 4. 점수보다 먼저 확인해야 할 것은 정보의 시점과 파이프라인의 일관성이다

- Oil Raw는 대회 제공 Test 값과 현실 예측 시점의 정보 가용성을 구분해야 한다.
- Fold마다 생성한 피처와 제출 시 생성한 피처의 병합·보간·범주형 처리 조건이 다르면 CV와 Public을 직접 해석하기 어렵다.
- **모델 성능뿐 아니라 입력 데이터가 언제 관측됐고 어떤 코드로 생성됐는지까지 실험의 일부로 기록해야 한다.**

### 느낀 점

- Day13에는 외부 데이터가 **올바르게 모델 입력까지 들어가는가**를 고민했다면, Day14에는 **검증에서 좋아진 모델이 실제 제출에서도 좋아지는가**를 확인하는 데 집중했다.
- Optuna로 더 낮은 Local 점수를 얻었을 때는 개선된 것처럼 보였지만, Public 결과는 반대였다. 이 경험을 통해 **최적화한 점수 자체보다 그 점수가 얼마나 믿을 만한지**가 중요하다는 걸 느꼈다.
- 반대로 이전 Local 실험에서 큰 성과가 없었던 Lag 364 관련 구성이 Public에서는 가장 좋은 결과를 냈다. 피처의 효과는 언제나 **함께 사용하는 피처, 평가 기간, 학습 설정**에 따라 달라질 수 있다는 점을 배웠다.
- 원인을 모를 때 과적합이나 누수라고 바로 결론 내리지 않고, **확인된 사실과 다음에 검증해야 할 가설을 분리하는 방식**으로 실험을 정리하려고 했다.
- **한 줄 정리: 좋은 CV 점수를 찾는 것에서 끝나지 않고, 그 결과가 실제 Test에서도 재현되는지 확인하는 것까지가 시계열 예측 실험이다.**

### 1. 다음 실험 계획 — Base23 + `sales_lag_364` 기준 개별 Ablation

이번 실험은 이전 `modeling.py`의 전처리·파라미터·3-Fold 검증 조건을 유지하고, **Base23 + `sales_lag_364` 24개**를 공통 기준 A로 삼는다. 각 후보는 A에서 **피처 하나만 추가**한다. Payday는 모든 구성에서 제외하며, **Optuna나 추가 파라미터 변경을 하지 않는다.**

| 실험 | 피처 구성 | 피처 수 | 비교 목적 |
|---|---|---:|---|
| **A (기준)** | Base23 + `sales_lag_364` | **24** | 공통 비교 기준 확보 |
| B | A + Oil Raw `dcoilwtico` | 25 | 원본 유가의 추가 효과 |
| C | A + `transactions_lag_16` | 25 | 16일 전 매장 거래량의 추가 효과 |
| D | A + `sales_lag_16` | 25 | 단기 Sales Lag 16의 추가 효과 |
| E | A + `sales_lag_28` | 25 | 단기 Sales Lag 28의 추가 효과 |

- 총 **5개 구성 × 3-Fold = 15회 모델 학습**을 계획한다.
- 최신 Public 0.43626의 `base23_payday_lag364_fixed`와는 **Payday 포함 여부 등 구성이 다르다.** 따라서 A의 CV를 기존 Public 점수와 같은 모델 성능으로 취급하지 않고, B~E의 효과를 분리하기 위한 새로운 공통 기준으로 사용한다.
- Transactions는 Test 기간의 당일 거래량을 알 수 없으므로 원본 `transactions` 대신 **`transactions_lag_16`**만 추가한다. 기존 `main()`의 Transactions 보간이 Fold 경계를 넘어 미래 정보를 사용했는지는 아직 확인되지 않아, **C의 누수 가능성 점검이 선행돼야 한다.**

**고정 조건**

| 항목 | 값 |
|---|---|
| 모델 | LightGBM (`gbdt`) |
| `learning_rate` / `num_leaves` | **0.05 / 31** |
| `max_depth` / `min_child_samples` | **−1 / 50** |
| `n_estimators` / Early Stopping | **8,000 / 150** |
| Random Seed | **42** |
| Target | **`log1p(sales)`** |
| Validation | **기존 16일 × 3-Fold** |
| 전처리 | **기존 `main()` 사용** |
| Optuna | **사용하지 않음** |

Early Stopping에 따라 Fold별 실제 Best Iteration은 달라질 수 있다. 변경 피처 외의 조건을 유지한 채 **A 대비 평균 RMSLE Δ, Fold별 개선 수, 표준편차**를 비교한다.

**실행 및 결과 저장 계획**

- 기존 `modeling.py`는 `final_submission.py`에서 사용하므로 **덮어쓰지 않고**, 별도 `src/modeling_overnight_ablation.py`로 실행한다.
- 먼저 `python src/modeling_overnight_ablation.py --check-only`로 필요한 컬럼과 입력 데이터를 검사한 뒤, 이상이 없으면 `python src/modeling_overnight_ablation.py`로 전체 실행한다.
- 중단되면 `python src/modeling_overnight_ablation.py --run-dir "results/base23_lag364_overnight/실행폴더명"`으로 완료된 Fold를 건너뛰고 재개한다.
- 결과는 `results/base23_lag364_overnight/실행시각/` 아래에 `run_config.json`, 진행 중 `fold_results_partial.csv`·`summary_partial.csv`, 완료 후 `ablation_summary.csv`·`ablation_fold_results.csv` 및 구성별 결과 폴더로 저장하도록 계획되어 있다.
- 공유된 코드 설명에서는 문법, 가상 데이터 Lag 생성, 피처 격리, LightGBM 학습, 저장·재개 동작을 시험했다고 하지만, **실제 약 300만 행의 전체 실행 결과는 아직 없다.** 또한 `main.py` 원본이 제공되지 않았으므로 Oil/Transactions 컬럼 매핑은 `--check-only`와 실제 코드 검토로 확인해야 한다.
