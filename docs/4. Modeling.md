# Modeling

> 현재는 첫 Baseline 구축 단계이다. LightGBM으로 판매량 예측 모델을 학습하고, 시간 순서를 유지한 Validation에서 성능을 평가했다. 첫 실험에서는 날짜·매장·상품군·프로모션·National Holiday 피처 19개를 사용했고, `n_estimators`를 1,000에서 1,300으로 늘려 **Validation RMSLE를 0.446059에서 0.440020으로 개선**했다. 이후 새로운 Feature Engineering과 하이퍼파라미터 변경으로 성능을 개선할 예정이며, 모델링 중 이상한 성능이나 문제가 발견되면 EDA/Preprocessing으로 돌아가 보완한다.

---

## 모델링 목표 및 평가 방식

이번 프로젝트의 목표는 **매장 × 상품군별 향후 16일간의 일별 판매량 예측**이다. 여러 매장과 상품군의 시계열이 함께 존재하는 패널 시계열 구조이므로, **하나의 LightGBM 모델**로 전체 시계열을 예측하는 방식을 선택했다.

### 평가 지표: RMSLE

Kaggle 대회의 평가 지표는 **RMSLE(Root Mean Squared Logarithmic Error)**이다.

$$
RMSLE = \sqrt{\frac{1}{n}\sum_{i=1}^{n}\left(\log(1+y_i)-\log(1+\hat{y}_i)\right)^2}
$$

- 실제값과 예측값에 `log1p()`를 적용한 뒤 RMSE를 계산한다.
- 판매량이 작은 상품군과 큰 상품군을 함께 평가할 때 로그 스케일의 오차를 반영한다.
- 음수 판매량 예측은 허용하지 않으므로 예측값을 0 이상으로 보정한다.
- **낮을수록 좋은 성능**이다.

### Target 설정

EDA와 전처리에서 `sales`가 매우 강한 right-skewed 분포임을 확인했으므로, 원본 대신 **로그 변환된 판매량을 학습 Target**으로 사용했다.

```python
train["sales_log"] = np.log1p(train["sales"])
```

학습 시에는 `sales_log`를 예측하고, 평가와 제출 시에는 역변환하여 원본 판매량을 복원한다.

```python
pred_sales = np.expm1(np.maximum(pred_log, 0))
```

- `np.maximum(pred_log, 0)`: 음수 로그 예측을 0으로 제한
- `np.expm1()`: `log1p()`의 역변환

> **판단:** 로그 Target의 RMSE는 RMSLE와 밀접하지만 음수 예측 보정 등이 있어 완전히 같지는 않다. 따라서 **최종 성능은 반드시 원본 판매량을 복원한 뒤 RMSLE로 계산**한다.

## Train / Validation 분리

시계열이므로 Random Split을 사용하지 않고, 실제 Test와 같은 길이인 **마지막 16일을 Validation**으로 설정했다.

| 구분 | 날짜 범위 | 데이터 수 |
|---|---|---:|
| Train | 2013-01-01 ~ 2017-07-30 | 2,979,504 |
| Validation | 2017-07-31 ~ 2017-08-15 | 28,512 |
| Test | 2017-08-16 ~ 2017-08-31 | 28,512 |

Train 데이터 수는 누락된 크리스마스 날짜에 0 판매량 행을 추가한 이후의 값이다. 이렇게 나눈 이유는 실제로 미래 16일을 예측할 때와 비슷한 환경을 만들기 위해서이다.

현재는 **마지막 16일 한 구간으로만 평가**하므로 특정 기간의 이벤트나 계절적 특성에 결과가 영향을 받을 수 있다. 향후 여러 시점의 16일 구간을 사용하는 Rolling Validation을 검토한다.

## Baseline 모델 선정

첫 모델은 **LightGBM Regressor**로 결정했다.

LightGBM은 Gradient Boosting Decision Tree(GBDT) 기반 모델이다. GBDT는 여러 결정트리를 순차적으로 학습하며 이전 모델의 예측 오차를 줄이는 방향으로 개선한다. 또한 일반적인 Level-wise 방식과 달리, 손실 감소 효과가 큰 Leaf를 우선 분할하는 **Leaf-wise 방식**으로 트리를 성장시킨다.

선택 이유는 다음과 같다.

- 매장 ID, 상품군, 날짜, 프로모션 등 **정형 데이터 피처**를 함께 학습할 수 있다.
- 수백만 행의 데이터를 비교적 **효율적으로 학습**할 수 있다.
- 복잡한 비선형 관계와 피처 간 상호작용을 학습할 수 있다.
- **Feature Importance**로 모델이 어떤 피처를 주로 활용했는지 확인할 수 있다.
- 피처 추가·제거 실험을 진행하기 쉽다.

> **판단:** 이번 Baseline의 목적은 최고 점수가 아니라 **향후 실험 결과를 비교할 기준 성능을 확보**하는 것이다.

```python
FEATURE_COLS = [

```

### 제외한 피처

| Feature | 제외 이유 |
|---|---|
| `id` | 행 식별자이므로 예측에 직접 사용하지 않음 |
| `date` | datetime 원본 대신 날짜 파생 피처 사용 |
| `sales` | 예측 Target |
| `sales_log` | 학습 Target으로만 사용 |
| `is_added_missing_date` | 전처리 과정의 추가 행 구분용 컬럼 |
| `holiday_count`, `holiday_types`, `event_groups` | 첫 모델에서는 제외 |
| `event_city_foundation` | National Holiday 기준 학습 데이터에서 활성화되지 않아 제외 |

### 현재 모델의 한계

첫 모델에는 **과거 판매량을 활용한 Lag 및 Rolling 피처가 없다.** 매장, 상품군, 날짜, 프로모션, 휴일 정보로 판매량을 예측할 뿐, 각 시계열의 최근 판매 흐름을 직접 입력받지는 않는다. 이는 향후 성능 개선에서 중요한 부분이 될 가능성이 있다.

## 범주형 변수 처리

`store_nbr`와 `family`는 실제로는 매장 ID와 상품군을 의미하므로 범주형으로 처리했다.

```python
CATEGORICAL_COLS = ["store_nbr", "family"]

for col in CATEGORICAL_COLS:
    X_train[col] = X_train[col].astype("category")

    X_valid[col] = pd.Categorical(
        X_valid[col],
        categories=X_train[col].cat.categories
    )
```

핵심은 **Train과 Validation의 범주 기준을 동일하게 유지**하는 것이다. `pd.Categorical()`의 `categories`에 Train의 범주 목록을 전달해 Validation이 별도의 범주 체계를 갖지 않도록 했다. 학습 시에도 해당 컬럼을 범주형 피처로 지정했다.

```python
categorical_feature=CATEGORICAL_COLS
```

이를 통해 매장 번호를 연속적인 숫자 크기로만 해석하지 않고 범주형 정보로 사용할 수 있다.

## 모델 설정

### 하이퍼파라미터

```python
model = lgb.LGBMRegressor(
    boosting_type="gbdt",
    objective="regression",
    learning_rate=0.05,
    n_estimators=1300,
    num_leaves=31,
    max_depth=-1,
    min_child_samples=50,
    min_split_gain=0.0,
    subsample=1.0,
    subsample_freq=0,
    colsample_bytree=1.0,
    reg_alpha=0.0,
    reg_lambda=0.0,
    metric="rmse",
    importance_type="split",
    random_state=42,
    n_jobs=-1,
    verbosity=-1
)
```

| Parameter | 역할 |
|---|---|
| `learning_rate` | 각 트리가 반영하는 학습 정도 |
| `n_estimators` | 최대 부스팅 반복 횟수 |
| `num_leaves` | 트리의 최대 Leaf 개수 |
| `max_depth` | 트리 깊이 제한 |
| `min_child_samples` | Leaf의 최소 데이터 개수 |
| `subsample` | 행 샘플링 비율 |
| `colsample_bytree` | 각 트리에서 사용하는 피처 비율 |
| `reg_alpha` / `reg_lambda` | L1 / L2 정규화 |
| `random_state` | 실험 재현성을 위한 난수 시드 |
| `importance_type` | 피처 중요도 계산 방식 |

초기 실험에서는 복잡한 튜닝 없이, 모델이 **기본 피처만으로 어느 정도 예측할 수 있는지** 확인하는 데 집중했다.

### 학습 및 Early Stopping

```python
model.fit(
    X_train,
    y_train,
    eval_set=[(X_valid, y_valid)],
    eval_metric="rmse",
    categorical_feature=CATEGORICAL_COLS,
    callbacks=[
        lgb.early_stopping(stopping_rounds=50),
        lgb.log_evaluation(period=50)
    ]
)
```

- `X_train`, `y_train`: 실제 모델 학습 데이터
- `X_valid`, `y_valid`: 학습 중 성능을 확인할 Validation 데이터
- `early_stopping(50)`: 50회 연속 개선되지 않으면 학습 중단
- `log_evaluation(50)`: 50회마다 평가 결과 출력

`n_estimators`는 최대 반복 횟수이고, `best_iteration_`은 Validation에서 가장 좋았던 반복 횟수이다. 이번 실험에서는 **모두 최대 반복 횟수까지 성능이 개선되어 Early Stopping이 발동하지 않았다.**

### Experiment 01 — 첫 Baseline

최대 반복 횟수인 1,000회에서도 Validation 손실이 계속 개선되고 있었으므로, 추가 학습을 실험해 볼 가치가 있다고 판단했다.

### Experiment 02 — Iterations 증가

입력 피처와 나머지 설정을 유지하고 `n_estimators`만 1,000에서 1,300으로 늘렸다.

| 항목 | Experiment 01 | Experiment 02 |
|---|---:|---:|
| Feature 수 | 19 | 19 |
| Learning Rate | 0.05 | 0.05 |
| Max Iterations | 1,000 | 1,300 |
| Best Iteration | 1,000 | 1,300 |
| Validation RMSE | 0.446283 | 0.440323 |
| **Validation RMSLE** | **0.446059** | **0.440020** |

$$
0.446059 \rightarrow 0.440020
$$

- 절대 감소: **0.006039**
- 상대 감소율: **약 1.35%**

> **판단:** 반복 횟수를 늘리자 성능이 개선되었다. 하지만 이것만으로 반복 횟수가 많을수록 항상 좋다고 볼 수는 없다. 트리 수가 늘면 학습 시간이 길어지고 특정 시점부터 과적합이 발생할 수 있다. 현재는 1,300회가 더 좋았으므로 **Experiment 02를 이후 실험의 비교 기준**으로 사용한다.

## Feature Importance 분석

Experiment 02의 Feature Importance를 확인했다. `importance_type="split"`이므로 값은 **해당 피처가 결정트리 분할에 사용된 횟수**를 의미한다.

| Feature | Split Importance |
|---|---:|
| `store_nbr` | 13,438 |
| `family` | 12,430 |
| `year` | 4,518 |
| `month` | 3,663 |
| `day` | 1,507 |
| `onpromotion` | 1,461 |
| `dayofweek` | 1,301 |
| `event_christmas` | 149 |
| `has_national_event` | 94 |
| `event_new_year` | 92 |
| `event_carnival` | 70 |
| `event_other` | 58 |
| `event_independence_day` | 52 |
| `is_promotion` | 51 |
| `event_mothers_day` | 34 |
| `event_good_friday` | 34 |
| `event_labor_day` | 26 |
| `is_weekend` | 22 |
| `onpromotion_log` | 0 |

### 1. 매장과 상품군의 중요도가 높음

`store_nbr`와 `family`가 가장 많은 분할에 사용되었다. 하나의 모델로 여러 시계열을 학습할 때 매장과 상품군을 구분하는 정보가 중요하게 쓰이고 있다는 뜻이다. 다만 Split Importance는 분할 횟수일 뿐이므로, 이 두 피처가 성능에 가장 크게 기여했다고 단정할 수는 없다.

### 2. 날짜 정보도 적극적으로 활용됨

`year`, `month`, `day`, `dayofweek`가 상대적으로 높았다. EDA에서 확인한 장기 추세와 날짜별 판매량 패턴을 모델이 활용하고 있을 가능성을 보여준다. 다만 어떤 계절성이나 추세를 정확히 학습했는지는 중요도만으로 증명할 수 없다.

### 3. `onpromotion`과 `onpromotion_log`의 차이

`onpromotion`은 1,461회 사용되었지만 `onpromotion_log`는 **한 번도 사용되지 않았다.** 같은 정보를 다른 형태로 제공했지만 모델은 원본 값만 활용했다. 다음 실험에서 `onpromotion_log`를 제거하고 성능을 비교할 수 있다.

### 4. Holiday 피처의 낮은 사용 빈도

Holiday 피처는 매장·상품군·날짜 피처보다 분할 횟수가 적었다. National Holiday만 사용하는 현재 방식에서는 지역별 휴일 효과가 충분히 표현되지 않았을 가능성이 있다. 그렇다고 유용하지 않다고 단정할 수는 없으므로, Holiday 피처를 제거하거나 지역 이벤트를 추가하는 **Ablation 실험**으로 실제 기여를 확인해야 한다.

## 발견한 인사이트

**첫째, 기본적인 정형 데이터 피처만으로 첫 예측 기준점을 확보했다.** 피처 19개를 사용한 LightGBM에서 Validation RMSLE 0.440020을 기록했고, 이제 이후 실험의 성능 변화를 객관적으로 비교할 수 있다.

**둘째, 매장과 상품군을 구분하는 정보가 모델에서 매우 자주 사용되었다.** 서로 다른 규모와 특성의 시계열을 하나의 모델로 학습할 때 범주형 정보가 중요한 역할을 할 가능성이 있다.

**셋째, 날짜 피처도 적극적으로 활용되었다.** EDA에서 관찰한 시간 변화가 모델링에서도 유용할 가능성을 확인했다. 구체적으로 어떤 패턴을 학습했는지는 추가 분석이 필요하다.

**넷째, 피처를 추가했다고 모든 피처가 활용되는 것은 아니다.** `onpromotion_log`의 Split Importance가 0이라는 점에서, 피처를 추가한 뒤에는 실제 사용 여부와 성능 기여를 확인해야 한다는 것을 배웠다.

**다섯째, Feature Importance와 성능 기여도는 구별해야 한다.** Split Importance는 사용 빈도를 알려줄 뿐, 해당 피처를 제거했을 때 RMSLE가 얼마나 변하는지는 알려주지 않는다. 실제 기여는 Ablation으로 확인해야 한다.

**여섯째, 학습 반복 횟수만으로도 성능이 달라진다.** 1,000회에서 1,300회로 늘리자 RMSLE가 약 1.35% 개선되었다. 하이퍼파라미터 변경은 같은 Validation 구간에서 비교해야 한다.

**일곱째, 현재 모델은 시계열 고유의 최근 판매 정보를 사용하지 않는다.** 최근 며칠간의 판매량이나 이동평균 같은 과거 판매량 피처가 없으므로, Lag/Rolling Feature Engineering이 주요 개선 방향이다.

**여덟째, Validation 성능과 Kaggle Public Score는 역할이 다르다.** Validation은 모델 개선과 비교에, Public Score는 제출 파이프라인 확인과 외부 평가 참고에 사용하는 것이 적절하다. Public Score만 반복해서 최적화하면 리더보드에 과적합할 위험이 있다.

### 한 줄 결론

> 날짜·매장·상품군·프로모션·National Holiday 피처로 첫 LightGBM Baseline을 구축했고, 학습 반복 횟수를 1,000회에서 1,300회로 늘려 Validation RMSLE를 0.446059에서 0.440020으로 개선했다. 현재 모델은 기본적인 정형 데이터 특성을 학습하고 있으며, 향후에는 최근 판매량과 매장·상품군별 시계열 패턴을 반영하는 Feature Engineering으로 추가 개선을 시도할 예정이다.
