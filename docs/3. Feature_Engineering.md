# Feature Engineering

> EDA에서 발견한 날짜·프로모션·휴일 패턴을 모델이 사용할 수 있는 Feature로 표현했다. 이번 단계에서는 **Date Feature, Promotion Feature, 범주형 처리, Holiday Event Group, 이벤트별 Binary Feature, National Holiday 병합 구조**까지 구현했다. Regional / Local 매칭과 Lag / Rolling Feature는 아직 진행하지 않았다. Holiday 병합 코드 중 일부는 다음 학습에서 자세히 분석할 예정이며, 각 Feature의 실제 기여도는 Baseline 모델의 Validation RMSLE로 확인한다.

## Feature Engineering 범위

이번 단계에서는 기존 데이터를 정리하는 **Preprocessing**과, 기존 정보에서 **새로운 설명 변수를 만드는 Feature Engineering**을 구분했다.

| 구분 | 작업 |
|---|---|
| Preprocessing (완료) | 날짜형 변환, 누락 날짜 복원, 원본 중복 제거, Target 로그 변환, Train/Validation 분리 |
| Feature Engineering (이번 단계) | 날짜 파생 변수, 프로모션 파생 변수, Holiday 그룹화, 이벤트별 0/1 변수, National Holiday 병합 |
| Feature Engineering (추후) | Regional / Local 매칭, Lag, Rolling, 매장·상품군별 통계 |

입력은 전처리가 끝난 `train_df`, `valid_df`, `test`, `holidays`이고, 결과는 `train_fe`, `valid_fe`, `test_fe`, `holidays_fe`로 관리한다.

이번 단계의 목적은 컬럼을 많이 만드는 것이 아니라,

> **EDA에서 발견한 패턴을 모델이 사용할 수 있는 정보로 표현하고, 이후 실험으로 효과를 검증할 수 있게 만드는 것**

이다.

### 생성 Feature 한눈에 보기

| 분류 | Feature | 비고 |
|---|---|---|
| Date | `year`, `month`, `day`, `dayofweek`, `is_weekend` | 5개 |
| Promotion | `onpromotion`(원본), `onpromotion_log`, `is_promotion` | 원본 보존 + 2개 생성 |
| Categorical | `store_nbr`, `family` | `category` 유지 |
| Holiday 그룹 | `event_group` | `description` 기반, 원본 보존 |
| Holiday Binary | `event_christmas`, `event_new_year`, `event_carnival`, `event_mothers_day`, `event_independence_day`, `event_city_foundation`, `event_other` | 7개, National만 |
| Holiday 집계 | `holiday_count`, `holiday_types`, `event_groups`, `holiday_descriptions`, `has_national_event` | 날짜별 집계 후 병합 |

## Date Feature

### 생성한 변수

EDA에서 전체 판매량의 **장기 추세**와 **요일별 차이**(목요일이 가장 낮고 주말, 특히 일요일이 높음)를 확인했다. 이 패턴을 Feature로 표현했다.

| Feature | 의미 | 값 |
|---|---|---|
| `year` | 연도 | 2013~2017 |
| `month` | 월 | 1~12 |
| `day` | 일 | 1~31 |
| `dayofweek` | 요일 | 월=0 ~ 일=6 |
| `is_weekend` | 주말 여부 | 0/1 |

### 구현

```python
def add_date_features(df):
    df = df.copy()

    df["date"] = pd.to_datetime(df["date"])

    df["year"] = df["date"].dt.year
    df["month"] = df["date"].dt.month
    df["day"] = df["date"].dt.day
    df["dayofweek"] = df["date"].dt.dayofweek

    df["is_weekend"] = (df["dayofweek"] >= 5).astype(int)

    return df
```

`date`를 datetime으로 바꾸는 것은 데이터를 쓰기 위한 전처리이고, 그 날짜에서 `.dt.year`, `.dt.month` 등을 추출하는 것은 새로운 정보를 만드는 Feature Engineering이다.

### 판단

- `year`: 장기 추세를 반영할 가능성. 다만 트리 모델은 학습 범위를 벗어난 추세를 외삽하지 못하므로, 추세는 이후 Lag / Rolling이 더 잘 표현할 수 있다.
- `month`: 월별·계절 패턴 구분
- `day`: 월초·월말 등 날짜별 차이 가능성. 아직 EDA 근거는 약하므로 기여도를 확인해야 한다.
- `dayofweek`: EDA의 요일별 판매량 차이를 직접 표현
- `is_weekend`: `dayofweek`에 이미 포함된 정보이므로 추가 개선이 있을지는 불확실하다.

> **판단:** EDA에서 확인한 시간 패턴을 기본 Feature로 표현하되, 각 변수의 기여는 모델링 결과로 확인한다.

## Promotion Feature

### 생성한 변수

EDA에서 `onpromotion`은 약 **79.6%가 0**이고 일부 큰 값이 있는 강한 right-skewed 분포였다. `sales`와 양의 상관(Pearson 약 0.426, Spearman 약 0.536)이 있었지만 상품군마다 강도가 달랐다. 그래서 원본을 보존하면서 두 가지 파생 변수를 추가했다.

| Feature | 의미 |
|---|---|
| `onpromotion` | 프로모션 중인 상품 수 (원본) |
| `onpromotion_log` | `log1p(onpromotion)` |
| `is_promotion` | 프로모션 상품이 하나라도 있는지 여부 |

### 구현

```python
def add_promotion_features(df):
    df = df.copy()

    df["onpromotion_log"] = np.log1p(df["onpromotion"])
    df["is_promotion"] = (df["onpromotion"] > 0).astype(int)

    return df
```

### 설계 이유

- **`log1p`**: `log(1+x)`라서 0이 많은 `onpromotion`에도 사용할 수 있다. 큰 값은 압축되지만 원본의 크기 정보를 대체하지는 못하므로 원본도 유지한다.
- **`is_promotion`**: 프로모션의 규모가 아니라 **존재 여부 자체**를 표현한다. 상품 수가 1개든 100개든 1이며, 실제 수량 차이는 원본 컬럼에 남아 있다.

### 판단

- 원본 수치, 로그 변환, 이진 여부는 서로 다른 정보를 줄 수 있어 모두 준비했다.
- 상품군마다 프로모션 효과가 다를 수 있지만, 이번 단계에서는 `family × onpromotion` 같은 상호작용 Feature를 만들지 않았다.
- 프로모션과 판매량의 상관관계를 인과로 해석하지 않는다.

> **판단:** 세 가지 표현을 모두 준비하고, 실제 효과는 Validation 성능으로 검증한다.

## Categorical Feature

`store_nbr`와 `family`는 값의 크기가 아니라 **그룹을 구분하는 ID**다. 매장 20번이 10번보다 두 배 크다는 의미는 없으므로 연속형 수치로 해석하면 안 된다.

| Feature | 의미 | 자료형 |
|---|---|---|
| `store_nbr` | 매장 ID | category |
| `family` | 상품군 | category |

```python
def add_categorical_features(df):
    df = df.copy()

    for col in ["store_nbr", "family"]:
        df[col] = df[col].astype("category")

    return df
```

전처리에서도 같은 변환을 했지만, 함수의 독립성을 위해 Feature Engineering 함수에도 포함했다.

### 판단

- **숫자로 저장되어 있다는 것과 연속형 변수라는 것은 다르다.**
- LightGBM은 범주형을 지원하지만, `category` 타입 처리와 모델 입력 설정은 Baseline 단계에서 따로 확인한다.

> **판단:** `store_nbr`, `family`는 범주형으로 유지하고 One-Hot Encoding은 하지 않는다.

## Holiday Feature

### 사용 컬럼

| 컬럼 | 의미 |
|---|---|
| `type` | 이벤트 종류 |
| `locale` | National / Regional / Local |
| `locale_name` | 실제 적용 지역 |
| `description` | 구체적인 이벤트 이름 |
| `transferred` | 휴일 이동 여부 |
| `event_group` | **새로 생성**한 이벤트 그룹 (원본 CSV에는 없음) |

`type`, `locale`, `locale_name`, `description`, `event_group`은 범주형으로, `transferred`는 불리언으로 유지한다.

### Event Group 생성

`description`에는 비슷한 이벤트가 서로 다른 이름으로 들어 있다. 예를 들어 `Navidad-4 ~ Navidad+1`은 모두 Christmas 관련 이벤트다. 이름을 그대로 쓰면 이들이 서로 다른 범주가 되므로, 유사 이벤트를 묶는 `event_group`을 만들었다.

```python
def add_event_group(holidays):
    holidays = holidays.copy()

    description = holidays["description"].fillna("").str.lower()

    holidays["event_group"] = "Other"

    event_patterns = {
        "Christmas": r"navidad",
        "New Year": r"primer dia del ano|ano nuevo",
        "Carnival": r"carnaval",
        "Mothers Day": r"dia de la madre",
        "Independence Day": r"independencia",
        "City Foundation": r"fundacion",
    }

    for group, pattern in event_patterns.items():
        mask = description.str.contains(pattern, regex=True, na=False)
        holidays.loc[mask, "event_group"] = group

    return holidays
```

| 코드 | 역할 |
|---|---|
| `fillna("")` | 결측값을 빈 문자열로 변경 |
| `str.lower()` | 대소문자 차이 제거 |
| `event_patterns.items()` | 그룹명과 검색 패턴을 함께 순회 |
| `str.contains(regex=True)` | 정규표현식 포함 여부 확인 |
| `.loc[mask, "event_group"]` | 조건에 맞는 행의 그룹 변경 |

먼저 모두 `Other`로 두고, 패턴에 일치하는 행만 그룹명으로 바꾸는 구조다.

### `description`과 `event_group`의 차이

| 구분 | description | event_group |
|---|---|---|
| 정보 | 구체적인 이벤트 이름 | 유사 이벤트 그룹 |
| 범주 수 | 많음 | 적음 |
| 장점 | 세부 차이 보존 | 공통 패턴 학습에 유리 |
| 한계 | 희소 범주, 과적합 가능 | 세부 정보 손실 |

어느 쪽이 더 좋은지 지금은 확정할 수 없으므로 **둘 다 보존하고 모델링에서 비교**하기로 했다.

### 현재 분류 규칙의 한계

- 같은 이벤트라도 표현이 다르면 `Other`로 분류된다.
- 한 `description`에 여러 패턴이 일치하면 **나중에 처리한 규칙이 덮어쓴다.**
- `Other`에는 성격이 다른 이벤트가 섞일 수 있다.
- EDA에서 구분했던 `Local Anniversary`, `Earthquake Event`, `Labor Day`, `Black Friday` 등은 아직 반영하지 않았다.

> **판단:** 기본 그룹부터 만들고, `Other`에 무엇이 들어 있는지 확인하면서 규칙을 보완한다.

## Event Group Binary Feature

### 생성 이유

Holiday 병합에서 가장 먼저 부딪힌 문제는 **같은 날짜에 여러 이벤트가 존재한다**는 점이다. 한 날짜에 대표 이벤트 하나만 남기면 나머지 정보가 사라진다. 그래서 이벤트 그룹마다 독립적인 0/1 Feature를 만들었다.

### 구현

```python
def add_event_binary_features(holidays):
    national = holidays[holidays["locale"] == "National"].copy()

    event_names = {
        "Christmas": "event_christmas",
        "New Year": "event_new_year",
        "Carnival": "event_carnival",
        "Mothers Day": "event_mothers_day",
        "Independence Day": "event_independence_day",
        "City Foundation": "event_city_foundation",
        "Other": "event_other",
    }

    for group, col in event_names.items():
        national[col] = (national["event_group"] == group).astype(int)

    event_cols = list(event_names.values())

    event_daily = (
        national
        .groupby("date")[event_cols]
        .max()
        .reset_index()
    )

    return event_daily
```

### 코드 이해

- 반복문에서 `group="Christmas"`, `col="event_christmas"`이면 `national[col]`은 `national["event_christmas"]`와 같다. 그룹마다 새 컬럼을 만들고 해당 그룹에 속하는지를 0/1로 기록한다.
- `(national["event_group"] == group)`의 결과는 `True/False`이고, `.astype(int)`가 이를 `1/0`으로 바꾼다.

### `groupby()`와 `max()`

같은 날짜의 이벤트를 하루 한 행으로 합치는 부분이다.

| 코드 | 역할 |
|---|---|
| `groupby("date")` | 같은 날짜의 이벤트를 묶음 |
| `[event_cols]` | 이벤트별 0/1 컬럼 선택 |
| `.max()` | 하나라도 있으면 1 |
| `.reset_index()` | 날짜를 일반 컬럼으로 복원 |

집계 전:

| date | event_christmas | event_other |
|---|---:|---:|
| 12-25 | 1 | 0 |
| 12-25 | 0 | 1 |
| 01-01 | 0 | 1 |

집계 후:

| date | event_christmas | event_other |
|---|---:|---:|
| 12-25 | 1 | 1 |
| 01-01 | 0 | 1 |

`.sum()`은 같은 그룹 이벤트가 여러 번이면 2 이상이 되지만, 이 Feature는 **발생 횟수가 아니라 존재 여부**를 표현하려는 것이므로 `.max()`가 목적에 맞다.

### 판단

- 같은 날짜에 이벤트가 여러 개여도 각각의 존재 여부가 보존된다.
- 이벤트 그룹 수가 늘면 컬럼 수도 늘어난다.
- 발생 횟수와 구체적인 이벤트 이름은 이진 변수로 표현할 수 없다. → `holiday_count`, 문자열 Feature로 보완한다.

> **판단:** 7개 그룹의 Binary Feature를 만들고, 문자열 집계 방식과 성능을 비교한다.

## Holiday Merge 설계

### 병합 시 발생하는 문제

판매 데이터와 Holiday 데이터는 행의 단위가 다르다.

> 판매 데이터: 날짜 × 매장 × 상품군 = 한 관측값
> Holiday 데이터: 한 날짜에 여러 이벤트가 존재할 수 있음

예를 들어 `2016-12-25`에 `Christmas`, `Other` 두 행이 있으면, 집계 없이 병합할 때 그 날짜의 판매 행이 **두 배로 늘어나** 같은 판매량이 중복된다. 따라서 **병합 전에 Holiday를 날짜별 한 행으로 만들어야 한다.**

### Inner Merge vs Left Merge

| 방식 | 결과 |
|---|---|
| Inner | 양쪽에 공통으로 있는 날짜만 남김 |
| Left | 판매 데이터 전체를 유지하고 Holiday 정보를 붙임 |

대부분의 날짜에는 Holiday가 없다. Inner Merge를 쓰면 일반 날짜의 판매 데이터가 사라지므로 **Left Merge**를 사용한다.

```python
df = df.merge(
    holiday_agg,
    on="date",
    how="left",
    validate="many_to_one"
)
```

`validate="many_to_one"`은 왼쪽(판매)은 날짜가 여러 번 나와도 되지만 오른쪽(집계)은 날짜가 유일해야 한다는 조건을 검증한다. 집계가 제대로 되지 않았다면 여기서 오류가 난다.

### National 이벤트만 병합하는 이유

| Locale | 적용 범위 |
|---|---|
| National | 전국 매장 |
| Regional | 특정 지역 매장 |
| Local | 특정 도시 매장 |

`stores.csv` 없이 Regional / Local을 날짜만으로 병합하면 해당 지역이 아닌 매장에도 이벤트가 적용된다. 그래서 현재는 **National만 전체 데이터에 적용**하고, Regional / Local은 `holidays`에 보존해 두었다가 이후 `stores.csv`의 `city`, `state`와 연결한다.

### 복수 이벤트 집계

National 이벤트를 날짜별로 묶어 다음 변수를 만든다.

| Feature | 의미 |
|---|---|
| `holiday_count` | 해당 날짜의 National 이벤트 행 개수 |
| `holiday_types` | 이벤트 종류 (중복 제거 후 결합) |
| `event_groups` | 이벤트 그룹 (중복 제거 후 결합) |
| `holiday_descriptions` | 구체적인 이벤트 이름 (중복 제거 후 결합) |
| `has_national_event` | National 이벤트 존재 여부 |

같은 날짜에 `Christmas`와 `Other`가 있으면 `Christmas|Other`처럼 하나의 문자열로 표현한다. 다만 LightGBM에서는 `Christmas`와 `Christmas|Other`가 서로 다른 범주가 되므로 이벤트별 Binary 방식과 비교해야 한다.

```python
holiday_agg = (
    national
    .groupby("date", observed=True)
    .agg(
        holiday_count=("type", "size"),

        holiday_types=(
            "type",
            lambda x: "|".join(sorted(set(x.astype(str))))
        ),

        event_groups=(
            "event_group",
            lambda x: "|".join(sorted(set(x.astype(str))))
        ),

        holiday_descriptions=(
            "description",
            lambda x: "|".join(sorted(set(x.astype(str))))
        )
    )
    .reset_index()
)
```

> **이 부분은 구현했지만 `.agg()`, `lambda`, `set()`, `sorted()`, `"|".join()`의 동작과 전체 흐름은 아직 완전히 분석하지 못했다. 다음 학습에서 자세히 분석한다.**

### 병합 후 결측치 처리

National 이벤트가 없는 날짜는 `left merge`에서 Holiday 컬럼이 결측이 된다. 다음처럼 "이벤트 없음"으로 표현한다.

| Feature | 결측 대체값 |
|---|---|
| `holiday_count`, 이벤트별 Binary | 0 |
| `holiday_types`, `event_groups`, `holiday_descriptions` | `"None"` |
| `has_national_event` | `False` |

- `has_national_event`는 실제 휴점 여부가 아니다. `Work Day`, `Event` 등 다양한 `type`이 섞여 있으므로 정확히는 **전국 단위 이벤트의 존재 여부**다.
- 문자열 컬럼을 `category`로 바꾼 뒤 `fillna("None")`을 쓰면 오류가 날 수 있다. **문자열 상태에서 채운 다음 category로 변환**하는 순서를 확인한다.

### 병합 검증

병합으로 판매 관측값이 늘거나 줄면 안 되므로 행 수를 비교한다.

```python
assert len(df) == original_rows, (
    "Holiday 병합 과정에서 행 수가 변경되었습니다."
)
```

Train, Validation, Test에는 같은 Feature Engineering 함수를 적용한다.

> **판단:** National 이벤트만 날짜 단위로 집계한 뒤 Left Merge한다. Regional / Local 매칭은 별도 단계로 진행한다.

## Test 기간과 Holiday Feature의 관계

EDA에서 확인한 Test 기간(2017-08-16 ~ 08-31)의 Holiday는 **2017-08-24 Ambato 도시 창립기념일 한 건(Local)**뿐이었다. 이를 지금 설계에 대입하면 다음이 보인다.

- 현재 병합하는 National Holiday Feature는 Test 기간에 **모두 0 / `"None"`** 이 될 가능성이 높다.
- 즉 Holiday Feature는 Train에서 크리스마스·연말 같은 특정 시기의 패턴을 설명하는 데는 도움이 되지만, **Test 예측에는 거의 기여하지 못할 수 있다.**
- 반대로 Test에 실제로 존재하는 유일한 휴일은 지금 병합하지 않은 Local 이벤트이므로, **Local 매칭의 우선순위가 높다.**
- `holiday_descriptions`처럼 범주가 매우 많은 Feature는 Train에 과적합되기 쉽고 Test에서는 항상 `"None"`일 수 있어, 유용성이 낮을 가능성이 있다.

> **판단:** Holiday Feature는 "Train 패턴을 올바르게 설명하는 도구"와 "Test 기간에 실제로 작동하는 도구"를 구분해서 평가한다. Baseline 이후 Local 매칭(Ambato)을 우선 진행한다. 위 내용은 EDA 결과에서 추론한 가설이며, 실제 Test 병합 결과로 확인해야 한다.

## Feature 표현 방식 비교

Holiday를 표현하는 방식은 하나가 아니므로, 각 방식의 장단점을 정리하고 비교에 필요한 정보를 모두 보존했다.

| 방식 | 장점 | 한계 |
|---|---|---|
| `event_groups` 문자열 집계 | 복수 이벤트를 한 컬럼에 보존 | 이벤트 조합별 희소 범주 발생 |
| 이벤트별 0/1 | 이벤트 존재 여부를 독립적으로 학습 | 구체적 이름·발생 횟수 부족 |
| `holiday_count` | 같은 날짜의 이벤트 수 표현 | 이벤트 종류는 알 수 없음 |
| `holiday_descriptions` | 세부 이벤트 정보 보존 | 범주 수 증가, 과적합 가능 |

### 실험 계획

기본 Feature(날짜·매장·상품군·프로모션)와 모델 설정을 고정하고 **Holiday 표현 방식만** 바꾸어 Validation RMSLE를 비교한다.

| 실험 | Holiday Feature |
|---|---|
| Base | Holiday Feature 없음 (기준점) |
| A | 문자열 `event_groups` |
| B | 이벤트별 Binary Feature |
| C | 문자열 + Binary Feature |

Base를 함께 두어야 Holiday Feature 자체의 효과와 표현 방식 간 차이를 구분할 수 있다.

> **판단:** 더 많은 Feature가 반드시 더 좋은 것은 아니다. 실제 모델 성능으로 각 표현 방식의 효과를 확인한다.

## 코드 구조 및 파이프라인

전처리와 Feature Engineering 코드를 연결하면서 실행 구조도 정리했다.

```text
src/
├── preprocessing.py
├── feature_engineering.py
└── main.py
```

| 파일 | 역할 |
|---|---|
| `preprocessing.py` | 데이터 로드, 날짜형 변환, Christmas 복원, 범주형 변환, Holiday 기본 정리, Train/Validation 분리, `sales_log` 생성, 전처리 QC |
| `feature_engineering.py` | `add_date_features()`, `add_promotion_features()`, `add_categorical_features()`, `add_event_group()`, `add_holiday_features()`, `add_event_binary_features()`, `merge_holiday_features()`, `apply_feature_engineering()` |
| `main.py` | 위 함수를 순서대로 호출해 전체 파이프라인 실행 |

```python
train_df, valid_df, test, holidays = run_preprocessing()

train_fe = apply_feature_engineering(train_df)
valid_fe = apply_feature_engineering(valid_df)
test_fe = apply_feature_engineering(test)

holidays_fe = add_holiday_features(holidays)

train_fe = merge_holiday_features(train_fe, holidays_fe)
valid_fe = merge_holiday_features(valid_fe, holidays_fe)
test_fe = merge_holiday_features(test_fe, holidays_fe)
```

### 해결한 오류

**1. Import 오류 (`NameError`)**
- 원인: `if __name__ == "__main__"` 내부의 코드는 파일을 **직접 실행할 때만** 실행된다. 다른 파일에서 import하면 그 안의 변수가 생성되지 않는다.
- 해결: 모듈에서는 **함수만 정의**하고, 실제 실행은 `main.py`에서 관리한다.

**2. `KeyError: 'event_group'`**
- 원인: `add_holiday_features()`에서 `event_group`을 범주형으로 바꾸려 했지만 원본 CSV에는 이 컬럼이 없었다.
- 해결: `add_event_group()`을 별도로 정의하고 자료형 변환 **전에** 실행하도록 수정했다.
- 배운 점: **Feature를 사용하는 코드보다 생성하는 코드가 먼저 실행되어야 한다.**

## 주요 결정

**첫째, Feature Engineering은 단순한 Feature부터 시작한다.** 날짜, 프로모션, 범주형, Holiday를 먼저 만들고 복잡한 시계열 Feature는 추후 추가한다.

**둘째, `onpromotion`은 원본과 로그 변환, 이진 여부를 모두 유지한다.** 어떤 표현이 더 효과적인지는 모델 실험으로 검증한다.

**셋째, `description`과 `event_group`을 모두 보존한다.** 세부 정보와 그룹 정보의 효과를 비교할 수 있게 한다.

**넷째, 복수 이벤트는 날짜별 집계와 Binary Feature로 함께 처리한다.** 같은 날짜에 이벤트가 여러 개여도 판매 행이 중복되지 않는다.

**다섯째, 최종 병합에는 Left Merge를 사용한다.** Holiday가 없는 일반 날짜도 학습에 필요하다.

**여섯째, 현재는 National 이벤트만 병합한다.** Regional / Local은 보존했다가 `stores.csv`와 연결하며, Test 기간의 유일한 휴일이 Local(Ambato)이므로 우선순위가 높다.

**일곱째, Feature 코드와 실행 코드를 분리한다.** 기능별 함수는 별도 파일에 두고 전체 실행은 `main.py`에서 관리한다.

**여덟째, Feature의 효과는 Validation RMSLE로 판단한다.** 직관적으로 유용해 보여도 성능 개선이 확인되지 않으면 재검토한다.

### 한 줄 결론

> Feature Engineering에서는 EDA에서 발견한 시간·프로모션·이벤트 패턴을 모델 입력 변수로 표현했다. 특히 복수 이벤트가 있는 Holiday 데이터는 단순 병합하면 판매 행이 중복되므로 날짜별 집계와 이벤트별 0/1 Feature를 설계했다. 현재는 National 이벤트만 적용했고, Test 기간의 휴일은 Local 이벤트이므로 지역 매칭이 다음 우선순위다. 각 Feature의 실제 기여도는 Baseline 모델의 Validation RMSLE로 검증한다.
