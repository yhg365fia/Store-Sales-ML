## 문서 기록 원칙

- **번호 부여 기준:** 실제 실행 결과가 확인된 실험에만 번호를 부여한다. 기존 Fold별 실험은 Experiment 01~30, 새로 확인된 파라미터 비교와 Optuna 두 건은 Exp 31~33, Public 제출 검증은 Exp 34로 구분한다. Day13 외부 5종은 개별 결과표가 없어 여전히 독립 번호 부여 보류.
- **번호 재배치:** 기존 예정 Experiment 03·04는 실행 순서에 맞춰 완료 실험으로 대체했고, 미실행 항목은 [향후 실험 후보](#향후-실험-후보-2026-10-26-갱신)로 옮겼다.
- **독립 실험 여부:** 별도 결과가 없는 피처 변경은 독립 실험으로 만들지 않았다. Rolling std를 하나씩 제외한 비교는 Exp 06의 후속 비교로 함께 기록했다.
- **이후 번호:** 결과가 추가되면 실행 순서대로 다음 번호를 부여한다.
- **조건 차이 표기:** 이전 결과와 최신 결과의 학습 상한·cutoff 차이를 구분해서 기록한다.
- **증거 수준:** Fold CSV·파라미터 JSON에서 재계산한 수치, Kaggle 화면의 Public 점수, 파일명으로 유추한 모델 구성, 미확인 원인 가설을 섞지 않는다. Train sample RMSLE는 전체 Train 성능이 아니다.

### 평가 지표와 타깃

- 평가 지표: RMSLE (낮을수록 좋음)
- 타깃 변환: `sales_log = log1p(sales)`로 학습하고 `np.expm1(np.maximum(pred_log, 0))`으로 복원한 뒤 원본 판매량 기준 RMSLE 계산
- 학습 중 평가 지표: 로그 타깃의 RMSE. 음수 로그 예측을 0으로 보정하므로 복원 후 RMSLE와 소폭 다를 수 있음
- 평균 RMSLE는 Fold 점수의 산술평균, 표준편차는 `pandas.Series.std()` 기본값인 표본 표준편차
- Exp 13~17·19~20의 Fold 간 표준편차도 Fold 점수에서 계산한 값

### 비교 규칙

- 단일 Validation과 3-Fold 평균은 직접적인 개선율 비교 대상으로 삼지 않는다. Exp 01~02와 비교할 때는 같은 기간인 Fold 3을 사용한다.
- 피처 변경 효과를 비교할 때 Fold, 모델 설정, Early Stopping 조건을 동일하게 유지한다. Best Iteration은 학습 결과에 따라 달라질 수 있다.
- Early Stopping 조건이 다르면 차이를 함께 표기한다. 피처 효과만의 비교는 Exp 05~11끼리 또는 Exp 12~17끼리에서만 성립한다. 같은 피처 구성인 Exp 05와 12의 차이는 Early Stopping 효과다.
- 검증 점수와 Kaggle Public 점수는 구분한다. Public 점수만 반복 최적화하지 않는다.
- Exp 18의 Public RMSLE는 전체 Train으로 재학습한 모델의 Test 16일 예측 점수다. 3-Fold 점수와 직접 비교하지 않고 Local과 Public의 차이를 함께 본다.
- Exp 31의 Train RMSLE는 요약 파일에 **in-sample Train의 일부 샘플 점수**로 표기된 값이다. Validation과의 차이를 일반화 갭의 근사 진단으로만 사용하며, Train/Valid의 기간·분포가 동일하다는 뜻이 아니다.
- Exp 32~33의 Optuna 최적값은 각 탐색 안에서의 최소 3-Fold 평균이다. **같은 데이터 분할로 여러 Trial을 선택한 데 따른 선택 편향**이 가능하므로 별도 시점 검증 또는 실제 Public 결과와 교차 확인한다.

### Feature Importance 기록 방식

- Exp 03~06: split(분기 사용 횟수) 기준
- Exp 07부터: split과 gain(분할로 줄어든 손실의 합)을 함께 계산
- best iteration 기준 값이며, Fold마다 학습량이 다르므로 Fold별 합계 대비 비율(%)로 환산한 뒤 평균
- 순위는 gain 기준이며 split 순위를 병기

## Experiment 05 — Rolling mean 추가

> **요약:** Rolling mean 7·14·28 추가(29개). 3-Fold 평균 **0.403774 → 0.393762** (−2.48%), 세 Fold 모두 개선. ES 50 기준 최고.

### 가설

- Lag는 특정 하루의 판매량이므로 일별 변동의 영향을 크게 받는다. 과거 여러 날의 평균을 함께 제공하면 매장 × 상품군의 판매 수준을 더 안정적으로 반영할 수 있다.
- 구간 길이를 7·14·28일로 나누면 단기와 중기 수준을 함께 제공할 수 있다.

### 변경 사항

- 비교 대상: Experiment 04
- 기존 26개 피처에 `sales_rolling_mean_16_7`, `sales_rolling_mean_16_14`, `sales_rolling_mean_16_28` 추가 → 총 29개
- 매장 × 상품군별 판매량을 16일 이동(`shift(16)`)한 뒤 `rolling(window=window, min_periods=window).mean()`으로 계산

## Experiment 07 — EMA 추가 (span 7·14·28)

> **요약:** EMA 3개 추가(32개). Fold 2만 개선, 평균 **0.393762 → 0.395270** (+0.38%). 개선 없음.

### 가설

- EMA는 최근 관측값에 더 큰 가중치를 주므로, 단순 평균인 Rolling mean이 반영하지 못하는 최근 판매 변화를 보완할 수 있다.

- Exp 16과 같은 패턴이다. Fold 1에서만 개선되고 Fold 2·3에서 악화돼 평균이 +0.26% 높아졌다. 여러 해를 평균해도 Lag 364 단독보다 나아지지 않았다.

# Phase 4. Kaggle 제출 (Exp 18)

## Experiment 18 — Kaggle 제출: Local과 Public 비교

> **요약:** Local 최고였던 Lag 3 + Mean 7·28이 Public에서는 **0.48334**로 Lag-only(**0.46161**)보다 약 4.7% 악화. 메인 Baseline을 Lag-only로 되돌림.

### 가설

- Local 3-Fold에서 Lag-only(0.403774)보다 Lag 3 + Mean 7·28(0.391424)이 크게 좋았으므로 Public에서도 개선될 것이다.
- Exp 13 Fold 3의 Best Iteration이 4,995로 상한에 근접했으므로, Full-train 반복 횟수를 늘리면(5,000) Public이 개선될 수 있다.

### 변경 사항

- 전체 Train(2013-01-01 ~ 2017-08-15)으로 재학습한 모델로 Test 28,512행(2017-08-16 ~ 2017-08-31)을 예측해 제출
- 제출 모델 3건

| 제출 모델 | 피처 수 | Full-train Iteration |
| --- | --: | --: |
| Lag 16·21·28 only | 26 | 4,044 |
| Lag 3 + Mean 7·28 | 28 | 4,335 |
| Lag 3 + Mean 7·28 | 28 | 5,000 |

- Full-train Iteration 4,335의 선택 근거는 기록하지 않음. 5,000은 Fold 3 Best Iteration이 상한에 근접했던 점을 확인하려는 설정

### 결과

| 제출 모델 | Full-train Iteration | Local 3-Fold 평균 | Fold 3 RMSLE | Public RMSLE | Public − Fold 3 |
| --- | --: | --: | --: | --: | --: |
| Lag only | 4,044 | 0.403774 (ES 50) | 0.406133 | **0.46161** | 0.055477 |
| Lag 3 + Mean 7·28 | 4,335 | **0.391424** (ES 150) | 0.394357 | 0.48334 | 0.088983 |
| Lag 3 + Mean 7·28 | 5,000 | 0.391424 (ES 150) | 0.394357 | 0.48431 | 0.089953 |

| 비교 | Local 3-Fold 평균 | Fold 3 | Public |
| --- | --: | --: | --: |
| Lag only → Lag 3 + Mean 7·28 (4,335) | −0.012350 (−3.06%) | −0.011776 (−2.90%) | **+0.02173 (+4.71%)** |
| Mean 7·28: 4,335 → 5,000 | — | — | +0.00097 (+0.20%) |
| Exp 02 제출(0.49044) → Lag only 제출 | — | — | −0.02883 (−5.88%) |

### 해석

- Local과 Public이 반대 방향으로 움직였다. Local에서는 Mean 7·28 추가가 평균 약 3% 개선이었지만 Public에서는 약 4.7% 악화됐다.
- Full-train Iteration을 5,000으로 늘리자 Public이 오히려 0.00097 더 나빠졌다. 따라서 이번 Public 저하를 4,335라는 반복 횟수 선택만으로 설명하기는 어렵다.
- Lag-only도 Local과 Public의 차이(Fold 3 기준 약 0.055)가 이미 컸다. Exp 02에서도 Validation과 Public 차이가 0.050이었다. Mean 모델은 이 차이가 약 0.089로 더 커졌다.
- 원인은 단정하지 않는다. 확인하지 않은 가능성은 다음과 같다.
  - Public은 Test 16일 한 구간의 점수라 변동이 크고, 검증 구간과 분포나 이벤트가 다를 수 있다.
  - Rolling mean을 포함한 제출 모델의 Test 피처가 3-Fold 검증과 같은 방식으로 생성됐는지 대조한 기록이 없다.
- Lag-only의 Full-train Iteration 4,044는 Exp 03 Fold 3의 Best Iteration과 같은 값이며, Exp 04 자체 3-Fold Best Iteration(949 / 1,768 / 2,387)과는 다르다. Lag-only 제출도 자체 3-Fold로 정한 반복 횟수는 아니다.
- 이 결과로 다음과 같이 정리했다.
  - **Local Champion:** Base 23 + Lag 16·21·28 + Rolling mean 7·28 (3-Fold 0.391424)
  - **Public Champion이자 메인 Baseline:** Base 23 + Lag 16·21·28 (3-Fold 0.403774, Public 0.46161)
- 검증 점수와 Public 점수를 구분하고 Public만 반복 최적화하지 않는다는 원칙에 따라, Public 단일 구간 결과만으로 피처를 평가하지는 않는다. 다만 Local 개선이 Public으로 이어지지 않은 사례로 기록하고 비교 기준을 Lag-only로 옮긴다.

### 다음 실험

  - 후보: `dayofyear`, 연간 sin/cos, 급여일(15일·말일), 월초·월말
- Lag-only baseline 0.403774는 Early Stopping 50 결과다. 이후 실험을 Early Stopping 150으로 진행한다면 Lag-only를 같은 조건으로 재측정해 비교 기준을 확정해야 한다.
- 비교 기준: Lag-only 3-Fold 평균 RMSLE **0.403774** (Early Stopping 50), Public RMSLE **0.46161**

## Experiment 20 — 연간 Calendar 표현 비교 (`dayofyear` vs sin/cos)

> **요약:** 6,500 상한에서 `dayofyear` 단독이 **0.394742**로 최고. sin/cos(0.398190), 결합(0.396700)은 제외. 채택 구성은 **27개 피처**.

### 가설

- `dayofyear`는 1~365(366)의 순서형 숫자라 12월 31일과 1월 1일이 수치상 멀리 떨어져 있다.
- 연간 위치를 sin/cos로 원형 인코딩하면 연말과 연초가 가까운 위치로 표현되므로, 반복되는 연간 패턴을 더 자연스럽게 전달할 수 있다.
- 반대로 LightGBM은 숫자 구간을 직접 분할할 수 있으므로 단순 `dayofyear`가 더 효율적일 가능성도 있다. 실제 3-Fold 성능으로 결정한다.

### 변경 사항

- Exp 19에서 일부 모델이 5,000 iteration 상한에 도달했으므로 `n_estimators=5000 → 6500`, Early Stopping 150 유지
- 공통 피처: 기본 23개 + Lag 16·21·28
- 비교 모델

| 모델 | Calendar 표현 | 전체 피처 수 |
| --- | --- | --: |
| A | `dayofyear` | 27 |
| B | `dayofyear_sin`, `dayofyear_cos` | 28 |
| C | `dayofyear`, `dayofyear_sin`, `dayofyear_cos` | 29 |

- sin/cos 계산: `angle = 2π × dayofyear / 365.25`, `dayofyear_sin = sin(angle)`, `dayofyear_cos = cos(angle)`
- Rolling / EMA / Lag364 / Payday는 사용하지 않음
- 세 모델 모두 같은 Fold, LightGBM 파라미터, Early Stopping 조건으로 학습

### 결과

| Fold | A. `dayofyear` | B. sin/cos | B − A | C. 결합 | C − A |
| --- | --: | --: | --: | --: | --: |
| 1 | 0.382917 | **0.380940** | **−0.001977** | 0.385058 | +0.002141 |

- 평균 순위: ① **`dayofyear` 0.394742** → ② `dayofyear + sin/cos` 0.396700 → ③ sin/cos 0.398190
- sin/cos 단독이 `dayofyear`보다 개선된 Fold: **1/3**, 결합 모델: **1/3**
- 따라서 연간 Calendar 표현은 **`dayofyear` 단독을 채택**하고 sin/cos는 제외한다.

- 중요도 분산 자체가 성능 악화의 원인이라고 확정할 수는 없지만, 추가된 sin/cos가 새로운 독립 정보라기보다 같은 연간 위치의 다른 표현이라는 점과 함께 볼 수 있다.

### 해석

- **더 많은 Calendar 표현이 더 좋은 성능으로 이어지지 않았다.** 27개 피처의 `dayofyear` 단독 모델이 28·29개 모델보다 평균 성능과 Fold 간 표준편차 모두 가장 좋았다.
- LightGBM은 `dayofyear <= 기준값` 형태로 날짜 구간을 직접 분할할 수 있어, 원형 좌표 두 개로 변환한 sin/cos보다 원본 위치 숫자가 더 간단한 표현이었을 가능성이 있다.
- 이번 3개 Validation 구간은 2017-06-29~2017-08-15로 이어지는 여름 구간이며, `dayofyear`로 약 180~227에 해당한다. 따라서 sin/cos의 대표적 장점인 **연말 365 ↔ 연초 1 경계 연결**을 Validation에서 직접 시험한 것은 아니다.
- 그러므로 sin/cos 자체가 항상 불리하다는 결론은 아니며, **현재 LightGBM + 현재 Validation 구간에서는 `dayofyear`가 더 적합했다**고 해석한다.
- `dayofyear`는 Fold 2에서 여전히 상대적으로 높은 오차를 보여 Calendar 피처 하나만으로 Fold 간 변동을 해결하지는 못했다.
- 현재 Calendar 단계의 채택 구성은 **Base23 + Lag 16·21·28 + `dayofyear` = 27개 피처**, 3-Fold 평균 RMSLE **0.394742**다.

## Experiment 29 — Group Statistics B: 매장 × 상품군 × 요일 평균 (확정 로그)

> **요약:** B 전용 실행 로그 확보. Gain 46.9275%로 30개 중 1위였지만 평균 **0.397647** (+0.003636, 약 0.92%) 악화, Fold 2만 개선. 채택 보류.

### 가설

- 같은 매장과 상품군이라도 요일마다 판매 수준이 다를 수 있으므로, `매장 × 상품군 × 요일`의 **과거 판매량 평균**이 Lag 16·21·28을 보완할 수 있다.
- 기존 A(`상품군 × 요일`), C(`매장 × 상품군`)와 달리 **세 가지 키를 함께** 사용하는 그룹 통계의 효과를 검증한다.

## Experiment 30 — Group Statistics F: 매장 × 요일, 일일 매장 총판매량 기반

> **요약:** `store_dayofweek_mean` 추가. 평균 **0.396725** (+0.002713) 악화, Fold 3만 개선(−0.001543). 채택 보류, Baseline 유지.

- 상품군별 평균(B) 대신 **매장 전체의 일별 총판매량**을 먼저 집계하면, 매장 단위의 요일별 방문·판매 규모를 표현할 수 있다.
- `store_nbr`와 `dayofweek`가 각각 존재하더라도, 매장별 요일 조합의 과거 평균은 추가 정보를 제공할 수 있다.

  - **Train:** 해당 날짜의 판매량은 계산에서 제외하고 과거 같은 요일 데이터만 사용
  - **Validation:** Fold Train 종료일까지의 집계 결과로 만든 평균을 **16일 검증 기간에 고정**. Valid `sales` 미사용

- 로그의 Fold 점수와 평균은 **소수점 6자리에서 동일**하다. 출력의 `-0.0`을 실질적인 개선으로 해석하지 않는다.
- 최초 제안한 전체 중요도 기반 선별적 Ablation 가운데 **실행 결과가 확인된 제거 피처는 `is_weekend`**이다. 다른 제거 실험을 완료로 기록하지 않는다.

### 해석

- 이번 3-Fold에서는 `is_weekend`가 없어도 성능이 표시 정밀도에서 유지되었다. `dayofweek`가 주말 구분을 이미 표현할 수 있기 때문이라는 설명은 **가능한 가설**이다.

- 28개 모델로 **복잡도는 피처 1개 줄었지만** 모델 일반화 성능이 개선됐다고 단정할 근거는 없다. 추후 선택할 경우 '동일 성능의 간소화 후보'로 판단한다.

| 구간 | Local CV | Public | 현재 판단 |
| --- | --- | --- | --- |
| Payday 29개 (Exp 27) | 0.394011 | 동일 구성 제출 점수 미첨부 | 과거 피처 실험의 고정 비교 기준 |
| Oil Raw 수동 Baseline (Exp 31) | 0.393282 | 0.50336 참조(설정 일치 미검증) | 내부 개선 여부와 제출 재현성 추가 확인 |

| Lag-only Optuna Trial 12 (Exp 33) | 0.393181 | 0.49487 | 과거 Lag-only Public보다 악화 |
| Lag 364 관련 제출 (Exp 34) | **미첨부** | **0.43626** | 현재 Public 최저, 재현/아블레이션 우선 |

**결론과 경계**

1. 모델 후보의 **CV 평가와 실제 Test/제출 파이프라인은 한 코드 경로**에서 재사용할 수 있어야 한다. 지금 보이는 큰 Local–Public 순위 역전은 그 일치성을 조사할 충분한 이유지만, 그 자체로 누수 또는 버그의 확증은 아니다.
2. **Optuna Trial 선택은 이미 해당 3-Fold를 여러 번 사용한 선택 결과**다. 탐색에 사용하지 않은 마지막 시점의 홀드아웃을 두거나 시계열 Nested CV를 검토한다. 16일 블록별 성능, 특히 마지막 Fold 및 달력·이벤트 분포를 관찰한다.
3. **Lag 364 효과는 분리 실험 대기.** 기존 Exp 16은 `Exp 13 + Lag 364`, 최신 제출은 이름상 Base23 + Payday + Lag364(정확한 목록 미확인)다. 두 실험이 다른 질문을 다룬다는 점을 보존한다.
4. **Train sample Gap은 보조 진단**이다. 사용된 Train 샘플의 시점/범위가 필요하며, Gap이 작거나 음수여도 Valid RMSLE 개선을 뜻하지 않는다. 중요한 선택 지표는 동일 조건의 시계열 외부 검증과 제출 확인이다.
5. `fold_results(3).csv`, `(4).csv`에는 **Trial 전체 하이퍼파라미터가 없다.** JSON은 Best Trial만 완전하게 기술한다. 동일 Trial들을 재실행하려면 Optuna Study DB 또는 Trial parameter log가 추가로 필요하다.

# 시간 누수 판단 기준

모델 성능 실험과 구분되는 **피처 설계 검토**이며, Experiment 번호는 부여하지 않는다.

- **핵심 판단 질문:** "해당 16일 예측을 시작하는 시점에 이 피처를 실제로 계산할 수 있는가?" 전체 과거 데이터를 한꺼번에 집계하더라도 Fold 경계를 넘는 정보가 섞이면 누수가 된다.

| 항목 | 판단 | 이유 |
| --- | --- | --- |
| 당일 집계 자체 (`groupby(["date", "store_nbr"])`) | 가능 | EDA 목적에서는 문제없음 |
| 당일 집계값을 같은 날 판매 예측의 입력으로 사용 | **누수** | `store_daily_sales`에 예측 목표 `sales`가 포함됨. Valid/Test 구간에서 미리 알 수 없는 정보이기도 함 |
| 과거 일별 집계값의 요일 평균 (F) | 가능 | Train 행은 자신의 날짜를 제외, Valid는 Fold Train 종료일 이전 정보만 사용 |
| `sales_lag_364` | 조건부 가능 | 예측 시작 시점 이전의 실제 `sales`만 읽어야 함. 16일 일괄 예측 기간에 364일 전 값은 과거 Train 영역에 있으나, 제출 구현의 조인·정렬 QC 필요 |
| Test 날짜 원본 Oil (`dcoilwtico`) | 대회 조건과 운영 조건을 분리 | 대회 제공 데이터에 미래 Oil 값이 있어도 현실 예측 시점에 그 값이 관측 가능한지는 별개 |
| Oil 결측 보간/뒤쪽 값으로 채우기 | 검증 누수 가능성 점검 | Fold Train의 미래 또는 Fold Valid/Test 관측을 과거 Train 피처에 사용했다면 당시 이용 불가능한 정보를 반영할 수 있음. 현재 사용된 정확한 보간 구현 미첨부 |

- **기존 A~E 및 B 수정 코드 점검:** Group Statistics는 Train의 전날 cutoff, Validation의 Train 종료일 cutoff를 기준으로 계산하도록 설계됐다. 같은 그룹·같은 날짜에 여러 행이 있으므로 단순 `groupby().shift(1)`로는 충분하지 않을 수 있고, 날짜별 합계·건수 + `merge_asof()` 방식으로 처리했다.
- **Lag 16/21/28, Rolling mean 및 EMA의 16일 Shift:** 16일 일괄 예측에서는 첫 Valid 날짜부터 마지막 날짜까지 참조하는 `sales`가 전부 Fold Train 영역에 있어야 한다. 현재 생성 코드의 Lag 최소 길이와 Rolling/EMA `shift(16)`는 이 조건에 부합한다. 단 실제 실행 파이프라인과 최종 Test 피처의 일치 여부는 별도 QC 필요.
- **Lag 364의 추가 QC:** 1,782개 시계열 × 364일 = 초기 결측 **648,648개 예상**(완전 일별 패널이라는 가정하에 계산한 기대값, 현재 최신 제출의 실측 로그 아님). 364일은 52주이므로 **요일 정렬** 효과를 가질 수 있지만, 정확한 연간 같은 날짜/휴일과 일치하는 것은 아니다. 효과는 별도 Ablation으로 검증한다.
- **Optuna Fold 재현성:** 모든 Trial에서 동일 3-Fold를 쓰더라도 전처리·스케일링·범주형 코드·Oil Fill이 Fold 경계 밖의 값을 읽지 않았는지 독립 점검한다. Kaggle Public의 악화만으로 누수가 확정된다고 주장하지 않는다.

# 최종 학습 / 제출 코드 준비 (실험 결과와 구분)

### 목적

- 최종 선택한 피처로 전체 Train을 학습하고 Test 예측 및 제출 CSV를 생성할 수 있도록 `final_submission.py` 준비

### 반영한 코드 흐름

1. 전체 Train + Test 연결 → 매장 × 상품군별 Lag 계산 → Train / Test 재분리
2. Test의 `sales`는 NaN으로 유지하고, Lag는 Train의 실제 과거 판매량에서 가져옴
3. Test 원래 순서 복원, 범주형 기준 통일, Test Lag 결측치 검사
4. 전체 Train으로 학습 → Test 예측 → `sample_submission.csv`의 id에 맞춰 병합 → CSV 저장

- Train 초기 Lag NaN은 허용하고 Test 입력 결측치는 금지
- 제출파일 행 수, id 일치, 판매량 결측치·음수·무한대 검사 포함

### 현재 상태 / 해석

- 코드 준비 후 전체 Train 재학습과 Kaggle 제출을 진행했다. 제출 결과는 Exp 18에 기록한다.
- 코드의 `BEST_ITERATION=4044`는 Lag 추가 전 Fold 3 결과(Exp 03)에서 가져온 값이며, Lag-only 제출은 이 값(4,044)으로 학습했다. 최종 학습 횟수는 최종 피처 구성의 3-Fold 결과를 반영해 결정해야 한다.
- Rolling mean을 포함한 모델(Lag 3 + Mean 7·28)도 같은 코드 흐름으로 제출했다(Exp 18). 메인 Baseline은 Lag-only로 되돌렸으므로, 이후 최종 학습 코드는 Lag-only 기준 피처와 반복 횟수를 따른다.
- Test의 Rolling mean도 Lag와 같은 방식으로 Train의 실제 과거 판매량에서 가져와야 하며, Test 입력 결측치 검사를 동일하게 적용해야 한다. 제출 모델의 Test 피처를 검증 구간 피처와 대조한 기록은 없다.
- Validation 없는 전체 학습에서는 Early Stopping 대신 정한 반복 횟수로 학습한다.
- CSV 저장 코드는 Kaggle 업로드를 자동 수행하지 않는다.
- **2026-10-26 추가 제출:** Oil Raw, Optuna Oil/Lag 및 `base23_payday_lag364_fixed`의 Kaggle 완료·Public 점수가 확인됐다(Exp 32~34). 하지만 이 사실만으로 **최신 제출 스크립트 코드, Best Iteration, Fold→Test 피처 생성 일치성, 실제 feature list**가 확인되는 것은 아니다.
- **현재 우선 재현 대상:** Public 0.43626의 Lag 364 관련 파일. 전체 Train 학습 전에 Fold 백테스트와 동일 생성 함수로 Test 특성을 빌드하고, 범주형 vocabulary·열 순서·각 Lag 관측일·NaN/Inf·28,512개 ID 일치·양수 예측 clipping 규칙을 체크한다.

- **평균 성능 개선이 확인되지 않은 Group Statistics:** A(초기/수정), B, C, D, E, F. 개별 Fold에서만 개선된 경우는 별도로 기술한다.
- **Ablation 실행 완료:** `is_weekend` 제거(29→28개), 3-Fold 6자리 RMSLE 동일. **다른 제거 후보는 아직 실험 완료로 단정하지 않는다.**

- **현재 Public 유망 모델:** Lag 364 관련 제출 **0.43626**. 피처·반복 횟수·CV를 아직 모르는 상태이므로 재현 전 최종 Champion으로 확정하지 않는다.
- **확인된 실패:** 수동 Oil 파라미터 변경 5종 모두 Baseline보다 악화, Oil Optuna는 CV 개선/Public 악화, Lag Optuna도 기존 Lag-only Public보다 악화. 단 원인(누수·과적합·코드 불일치)은 미검증으로 분류한다.
- 피처 실험 간 **같은 Fold, Baseline 버전, cutoff, 학습 상한, Early Stopping**을 맞춰 비교한다. 저장 점수를 재사용할 경우 그 사실을 명시한다.
- 새 실험은 반드시 **가설 → 변경 사항 → 결과 → 해석 → 다음 실험**과 Best Iteration·RMSLE·중요도·QC를 포함해 기록한다.
